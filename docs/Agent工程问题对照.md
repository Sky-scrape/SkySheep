# Agent 工程问题对照（13 题体检表）

2026-11-15 整理：用一组业界高频的 Agent 工程问题（原题出自阿里巴巴大模型
Agent 面试题）逐题对照 SkySheep 的实现——哪些已经有实体机制、哪些是本日
补上的关键缺口、哪些明确不做并记下理由。后续做架构决策时可当体检表复查；
对外讲设计含金量时也可直接引用对应模块。

状态口径：✅ 已有实体机制；➕ 本批（2026-11-15）补齐关键缺口；⏸ 明确不做（记录理由）。

## 逐题对照

### 1. ReAct 推理—行动循环在长程任务中为什么退化？如何设计更稳的规划—执行分离？

✅➕ **现状**：`core/agent.py` 单循环 + `LoopGuard`（`core/loop_guard.py`）拦「同参数
+ 同结果」的原样重试与同工具反复撞同一错误；`todo_write` 工具承载任务清单；
规划—执行分离走子代理（同步/后台/隔离 worktree）与团队 AI 总管（拆解→派工→
收报→验收）。
**➕ 本批**：计划锚点自检（`[agent].drift_check_steps`，默认 6，0=关）——长任务每
N 步把 todo 清单进度注入一次最后一条工具结果，提醒模型对照用户最初的目标自查
漂移。语义级漂移没有便宜的机械判据，用「定期拍计划」代替在线检测，且不额外
发模型调用（复述要求写在提醒里，由模型在下一步自己的输出里完成）。评测基线
场景 37。

### 2. 工具选择的置信度校准？误调用与漏调用如何建模优化？

⏸ **不做显式置信校准器**。理由：真校准需要「该用没用/用错」的标注数据，
桌面单机产品没有在线流量去收集；且 SkySheep 的工具误用损失主要由权限门与
参数校验兜底（pydantic `args_model`、白名单按实际 shell 判拼接）。已有的替代
信号：工具报错计数与重复调用计数（见第 6 题）、`LoopGuard` 熔断、事后巡检。
漏调用的「该用没用」检测成本高于收益，跟随评测场景积累，不在运行时强做。

### 3. 多工具组合调用的依赖编排、参数校验与中间结果一致性？

✅ **核查为已存在**（与 2026-11-15 批次的 O3 同性质）：参数校验在工具层统一走
`args_model`（pydantic）；编排载体 pipeline 工具对节点做引用校验与成环检测
（`_validate_deps` → `store._check_dep_refs` + `has_dependency_cycle`），运行中
流水线拒改节点（防预授权面热替换）；并行写同一文件的协调在 `security/leases.py`
写租约。中间结果一致性（执行期）属自动化执行器语义，依赖失败级联已有评测
场景 9 钉住。

### 4. 长上下文下记忆的写入、检索、遗忘与冲突消解？

✅➕ **现状**：写入=memory_write（引擎主目录 memory.md，逐次确认）+ 记忆地图
摘要；检索=`retrieval.py` 零依赖 BM25+余弦混合排序（可选 Ollama 向量，失败
一律回落纯关键词）；遗忘/整理=定期整理循环 + 归档提炼 + 总闸，维护提示词
里明确「删除明显过时、与其它条目矛盾的内容」。
**➕ 本批**：写入时冲突标注——新条目与现有条目 difflib 相似度 ≥0.72 时在工具
结果里点名旧条目提示核对（旧条目不再成立时用 delete 删），新信息照常落盘不
拦截。写入当下模型还知道来龙去脉，提示顺手删旧条目成本最低，不再只等定期
整理兜底。评测基线场景 38。

### 5. 上下文压缩/摘要丢信息，如何评估压缩对决策质量的影响？

✅➕ **现状**：有损摘要 + 原文 Spill——被摘要替换的段落原子落盘
`<项目>/.skysheep/transcripts/`，摘要末尾附续读指针，落盘失败降级为只摘要。
评测基线场景 17/18 钉触发边界与压缩后结构。
**➕ 本批**：场景 35 把「压缩不丢信息」钉在机制链路上：被替换的关键事实一字
不差存在于 transcript、摘要尾部指针指向它。摘要文本质量归真实模型（评测层
不评措辞），但只要「原文落盘 + 指针在」两样可断言，被压掉的事实永远可找回。

### 6. 长程任务的信用分配：某一步工具调用对最终结果是否有贡献？

➕ **做轮级代理信号，步级归因明确 defer**。完整逐步归因（每步对最终结果的
贡献度）需要反事实重放或训练价值模型，单机产品成本不成立。本批先落「无效
步骤」的客观计数：每轮 obs 结构化日志增 `dup_tool_calls`（同工具+同参数的
再次尝试数）；`usage_log` 增 `tool_calls`/`tool_errors` 列（用量页出工具报错率）；
自动化账本 `automation_runs` 增 `tool_errors`，巡检提示词据此新增「工具报错
很多但状态仍是完成（带病跑完）」判定线索。有数据沉淀，步级归因以后才有的做。

### 7. RAG、工具调用和记忆三者的路由边界？路由错误如何检测与回退？

✅➕ **现状**：路由由模型按工具描述自主完成；检索类失败有回退（Ollama 向量
失败回落 BM25、BM25 是零依赖底线）。
**➕ 本批**：`search_documents` 零命中且索引在时给换路提示（换更具体词/缩小
path；可能不在本项目文档里的改用 web_search；想通读原文用 read_document）——
防模型在「换词重试」上空转。单元测试钉两种零命中形态。

### 8. 多智能体系统的通信拓扑、角色分工与共识机制对稳定性与成本的影响？

✅ **主打能力**：圆桌=星型（成员并行作答、主席融合即共识）；团队=频道+工单板
+总管（用户总管或 AI 总管闭环，验收/打回/改派）；对抗=发现→调查→建议→裁判
四角色流水线（不对称激励+阶段上下文隔离）。成本护栏：融合草稿总预算、成员
轻上下文、同 provider 并发信号量、max_rounds 全局轮次、stall_limit 停滞移交、
token 预算越线强制交付。

### 9. Agent 陷入循环、目标漂移或过早终止，如何在线检测与恢复？

✅➕ **现状**：结构性检测齐——LoopGuard（打转）、团队 stall_limit（停滞移交
总管）、redo 超限注入强制裁定、token 预算越线强制交付、检查点+回滚、取消/
重试链路。
**➕ 本批**：语义级目标漂移走第 1 题的计划锚点（每 N 步对照原目标自查）——
与结构性检测互补：结构信号管「在打转」，锚点管「没打转但在做别的」。

### 10. 可复现的 Agent 评测？LLM-as-judge 的偏差与评测污染如何控制？

✅➕ **现状**：`engine/evals/` 行为级基线（38 个编号场景，fake provider 驱动真实
循环+真实权限门，不联网、隔离 home）+ 指标插件（token/工具次数/确认次数/
重试，逐条落 JSONL）；LLM-as-judge 是可选层不进默认回归。
**➕ 本批**：judge 反偏置——评分提示词固定加入长度中性（不以写得多加分）与
「只依据问题与标准、不引入外部知识」；新增 `judge_compare` A/B 对照评审：
评审两次（第二次换序），两次 winner 一致才判 consistent，不一致返回
needs_human 交人工，不强行采信（位置偏差是 LLM-as-judge 的已知问题）。评测
污染的隔离靠 evals 不进默认套件、评测集与实现分层（tests 钉函数、evals 钉组装）。

### 11. Prompt Injection 与工具越权：架构层如何做权限隔离与最小授权？

✅➕ **强项，多层已有**：权限三档（只读自动放行/写执行确认/完全访问）+ 命令
白名单按实际 shell 判拼接（Windows cmd 单引号与 %VAR% 都算拼接面）+ 出站
密钥预拒绝；web_fetch 的「框起来+标记」两态、站点信任级、隔离区模式（全文
落盘模型只见摘录）、SSRF 逐跳校验；`read_document`/`search_documents` 外部
内容包「数据不是指令」标注；工作区信任（不自动执行仓库自带 .skysheep 配置）；
渠道/无头门的无人值守自动拒绝；GrantedGate/IsolatedGate/TeamIsolatedGate 收窄。
**➕ 本批**：web_search 结果接同一层防线——标题/摘要包进带 nonce 的数据区
标注（正文一字不改、只标记不拦截）。此前搜索通道是注入防御的漏网通道：网页
可以把话术直接写进搜索摘要。单元测试 + 评测基线场景 36。

### 12. 生产环境中延迟、成本、成功率与可观测性的权衡？关键取舍？

✅➕ **现状**：obs 结构化日志（每轮总耗时/工具次数与耗时/最慢工具/权限等待/
token，`|json|` 尾注按会话可检索）；用量页 token 口径 + 每日/单轮预算护栏 +
超限渠道推送；任务耗时预估（task_estimate，中位数校准）；思考强度自动估档；
流式增量合并降帧；MCP keeper 超时与有界退避重连。
**➕ 本批**：`usage_log`（v14）增 `tool_calls`/`tool_errors`/`failed` 三列——用量
页新增「近 N 天 X 轮：成功率 Y%（失败 Z 轮，主动停止不算失败）· 工具调用 A
次、报错 B 次（C%）」。口径：引擎级失败（异常/ErrorEvent/stop_reason=error）
算 failed，用户主动停止不算；旧记录与协作路径三列为 0，无数据不展示（不出
「成功率 100%」假象）。

### 13. 设计可回滚、可审计、可限流的 Agent 执行引擎：核心模块与状态机？

✅ **三性都有实体**：可回滚=检查点（会话回滚，冲突脏检查）+ move_file/
delete_file 可撤销（命令改动不进检查点，所以不教模型用 mv/rm）；可审计=全程
AgentEvent 事件流落库（NDJSON 无头协议同源）+ 权限决策与白名单沉淀持久化 +
结构化日志；限流=max_iterations 轮次上限、token 预算双护栏、同 provider 并发
信号量、写租约冲突等待上限、MCP 重连退避、巡检/整理的间隔节流。执行「状态
机」以事件流为准（turn_started→tool_call_started/finished→turn_finished，
stop_reason 显式枚举：end_turn/max_iterations/error/cancelled），无隐式状态。
