# 团队模式设计（概念稿）

> 状态：一、二、三期已实施（一、二期 2026-10-06，三期 2026-10-07），四期待推进。本文是「团队」功能的唯一概念来源，
> 实施按 §11 分期推进；术语落地后按 §12 并入 `docs/界面术语表.md`。概念基线版本：2.4.1（2026-10-06 定稿）。
> 设计原则：与圆桌并列、不替代圆桌；安全模型零放松；能复用的设施全部复用（见 §10）。

## 1. 定位：圆桌 vs 团队

| | 圆桌（已上线） | 团队（本设计） |
|---|---|---|
| 一句话 | **会诊**：同一问题平行作答 → 主席融合 | **开工**：一个目标分工协作 → 验收交付 |
| 协作拓扑 | 成员互不通气（辩论轮只读上一轮静态草稿快照） | 团队频道互通 + 总管中枢裁定 |
| 成员工具 | 无工具，纯文本 | 分级混编：执行型带工具干活 / 顾问型只出意见 |
| 时效 | 一次问答内完成 | 跨多轮持续（会话级活动团队） |
| 主持者 | 主席只做终局融合，不参与过程 | 总管全程编排：拆解、派工、验收、裁定、交付 |
| 产出 | 一份融合回答 | 一批工单成果 + 《交付说明》 |

- 两者是**并列**的两种多模型协作模式，入口并列（输入栏圆桌开关旁加团队开关），互不替代；同一轮二者互斥（见 §13.4）。
- 团队处理重大分歧时的「小会」复用 `run_roundtable`（`core/roundtable.py`）——圆桌作为团队的内嵌表决原语，这是两者唯一的运行期交点。

## 2. 角色体系

### 2.1 总管（唯一）

职责链：拆解目标 → 产出《分工方案》→ 按依赖派工 → 催办 → 逐单验收（不合格打回附理由）→ 裁定分歧 → 汇总《交付说明》。

建队时二选一：

- **用户总管**：用户本人当总管，逐条下达指令推进团队（每条消息就是一道总管指令，直达频道）；队员向用户请示；用户可在团队频道 @队员请其代拟草稿（《分工方案》的 AI 自动产出属 AI 总管模式）。节奏完全由用户控制，最稳，是一期形态。
- **AI 总管**：从已配 Key 的模型中指定一个担任总管，自动运转拆解→派工→验收→交付。用户保留三样随时可用的权力：**插话**（以最高优先级注入总管下一轮）、**接管**（切回用户总管）、**收队**（立即终止）。AI 总管默认不兼任队员、不领工单（角色纯粹，避免自验收；见 §13.2）。

### 2.2 队员（2~8 名）

- 每个队员 = `(provider, model)` + 成员名（默认取 provider 名，可自定义如「小研」「写手」）+ 一句话人设（写进该成员系统提示词；比圆桌 `MEMBER_ROLES`（`core/roundtable.py:73`）的四选一预设更自由）。
- **分级混编**：执行型 / 顾问型是**工单级**属性，不是成员级——总管派工时逐单指定。同一队员这一单被指定为执行型（挂完整工具注册表，真实读写文件/跑命令/联网），下一单被指定为顾问型（挂空工具表，同圆桌成员，只出分析与建议）。
- 队员各自拥有独立 history，互不可见；彼此同步只靠团队频道（§4）。成员 Provider 实例化复用 `server/backend.py` 的 `_build_member_provider` / `_resolve_members`。

### 2.3 用户（最高裁决者）

无论谁当总管：插话、否决、接管、收队永远可用；**权限确认只认用户**（§6）。

## 3. 生命周期（六阶段）

```
组队 → 立约 → 开工 ⇄ 协商 → 验收 → 交付 → 归档
              （开工与协商交叠进行）
```

| 阶段 | 进入方式 | 内容 |
|---|---|---|
| 组队 | 输入栏开团队开关后发送首条消息 | 选总管形态、成员名单与人设、参数；发 `TeamStarted` 事件 |
| 立约 | 组队后自动进入 | 产出《分工方案》：目标重述 + 工单清单（每条含编号/标题/指派队员/执行型或顾问型/依赖工单/验收标准）+ 协作约定。用户总管模式下由用户起草（AI 可代拟草稿）；AI 总管模式下由总管产出并展示给用户 |
| 开工 | 《分工方案》就绪 | 总管按依赖关系派发工单（可并行）：`assign` 消息 + 工单板置「进行中」；被派队员被唤醒执行 |
| 协商 | 与开工交叠 | 队员在频道汇报进展 / 请示 / 请求协助 / 提出异议。分歧三级处理：① 队员间频道互聊自行解决 → ② 谈不拢 @总管裁定 → ③ 重大分歧由总管开「小会」快速表决（§4.3） |
| 验收 | 队员交报告（`report` 消息，工单置「待验收」） | 总管逐单验收：通过置「完成」；不合格**打回**（`ruling` 消息附理由，工单回「进行中」，redo+1），redo 超上限强制裁定（§9） |
| 交付 | 全部工单完成，或触发任一停机条件 | 总管产出《交付说明》：成果汇总、各队员贡献、未尽事项；发 `TeamFinished`，团队进入终态 |
| 归档 | 交付后 | 全过程随会话落库可回放；可「另存为团队模板」（名册+人设+总管配置，三期） |

**活动团队是会话级状态**：团队进行中（未交付、未收队），该会话的后续消息不进普通回合——用户总管模式下每条消息作为总管指令进频道；AI 总管模式下作为用户插话注入总管。团队卡在聊天流中保持展开。交付/收队后恢复普通回合。应用重启时，进行中的团队一律标注「已中断」，不自动恢复（沿子代理任务簿的重启处置先例）。

## 4. 通信模型（团队频道）

### 4.1 频道

- 全员共享**团队频道**（共享消息簿），消息按 `seq` 单调递增。注意：团队频道与聊天机器人「渠道」（飞书/微信）是两个词两回事，文案中严格区分。
- 消息结构：`{seq, from, to, kind, text, task_ref, ts}`
  - `from`：成员名 / `director` / `user` / `system`
  - `to`：`all`（广播）/ 成员名（@定向）/ `director`
  - `kind`：`assign` 派工 / `report` 汇报 / `ask` 请示 / `help` 协助请求 / `object` 异议 / `ruling` 裁定 / `system` 系统
  - `task_ref`：关联工单编号（可空）
- 频道消息是**纯文本**，任何情况下不直接执行（§6.4）。

### 4.2 调度（事件驱动唤醒，不自由抢话）

- 成员不抢话，由调度器按事件唤醒：被派工 → 开工轮；被 @ → 应答轮；自己的工单完成 → 汇报轮；总管催办 → 答复轮。顾问型队员仅在被 @ 或被派顾问型工单时唤醒。
- 唤醒机制复用子代理的轮首注入模式（`core/subagent.py` 的 `_turn_notes` + `server/backend.py:1861` 的 `pop_turn_note` 接线）：定向消息/新工单注入目标成员下一轮上下文；广播消息在该成员下一次自然发言前批量注入，不打断正在跑的轮。
- 成员上下文窗口（token 经济核心）：只注入「频道未读消息（裁剪）+ 自己名下工单及状态 + 相关报告摘录」，**不共享**其他成员 history、不注入全量会话历史。单条频道消息限长（§9），超长全文落盘、只投摘录（复用 `core/subagent.py` 的 `REPORT_INLINE_LIMIT = 2400` 落盘+摘录投递机制）。

### 4.3 小会（huddle）

总管对重大分歧发起：指定 2~3 名相关队员就**单一争议**各表一轮意见（互相可见），总管收口裁定。实现上复用 `run_roundtable`（辩论 1 轮 + 融合者=总管），争议问题由总管拟定。

## 5. 工单模型

> 叫「工单」不叫「任务」——「任务」在界面术语表已是右面板容器词（子代理任务/任务清单/项目任务），不得叠加第六义。

- 字段：`{id, title, assignee, type(执行型|顾问型), deps(依赖工单), accept(验收标准), status, redo, result_ref}`
- 状态机：

```
待办 ──派工──▶ 进行中 ──交报告──▶ 待验收 ──验收通过──▶ 完成
                  ▲                  │
                  └─────打回(redo+1)──┘
```

- 规则：依赖工单未完成不派发；单工单 redo 上限默认 2，超限由总管强制裁定（改派他人 / 降级为顾问型 / 砍掉并记入未尽事项）；工单成果超长走落盘摘录。

## 6. 权限与安全

安全模型零放松，团队不新增任何绕过：

1. **权限三档照旧**：只读自动放行、写/执行需确认。执行型队员的工具调用一律经过各自的 `PermissionGate`（`security/gate.py`）。
2. **前台冒泡带来源**：用户总管模式 / 同步在场的执行型队员，权限请求复用 `PermissionRequest` 事件的既有 `note` 字段带来源标注（「来自队员『小研』…」）冒泡给用户，确认只认用户。
3. **AI 总管队员同走前台冒泡（二期落地口径，2026-10-06 评审修订）**：原设计按一、二期沿用 `SubagentGate`（`core/subagent.py:102`）的预拒绝+报告转述、三期再升级实时确认；实际二期落地时 AI 总管闭环在用户在场的同步轮内运行（团队没有后台派生路径），执行型队员与用户总管同属 §6.2 的「同步在场」——权限请求经 `TeamMemberGate`（`core/team.py:532`，会话既有 `PermissionGate` 的来源标注代理、决策零改变）实时确认，比预拒绝更严且有测试背书（`tests/test_team.py`：AI 闭环停在成员写确认点，接管在确认点干净取消）。预拒绝+报告转述是未来「无人在场的后台团队运行」（四期候选）才需要的保守门，二期不接入。
4. **提权链防护**：频道消息纯文本不可执行；总管无权替队员放行权限；决策值过 `normalize_decision` 白名单 fail-closed 的既有语义不变。杜绝「总管让队员自我授权」。
5. **并行写协调**：复用写租约（`security/gate.py:775` 的 `claim_write`，枢纽在 `security/leases.py`）。
6. **隔离派生（四期候选）**：改代码工单可走 `core/worktree.py` 隔离 + `IsolatedGate`（工作区内写放行、命令预拒绝、完成自动提交）。
7. **无人值守（四期，规格已定 §14）**：定时任务里跑团队用 `HeadlessGate` 名单制 fail-closed。
8. **联网底线**：队员联网仍走 `web_fetch` 既有 SSRF 防护，不因团队模式放宽。

### 7.1 事件（`events.py` 正式注册，进 `AgentEvent` 联合）

| 事件 | 关键字段 | 说明 |
|---|---|---|
| `TeamStarted` | roster[{index, name, provider, model, persona}]、director{mode, model?} | 组队完成 |
| `TeamMessageDelta` | member_index、seq、text | 发言流式增量；`server/backend.py:200` 的 `_MERGEABLE_DELTA_KINDS` 加一员，按 member_index 分桶合并 |

| `TeamFinished` | status(done/aborted/rounds_exhausted/budget_exhausted)、summary | 交付/终止 |

### 7.2 前端（一期做聊天流内团队卡，仿圆桌卡）

- 卡头：名册（头像复用 `static/logos/` 厂商 logo）+ 总管标识 + 阶段徽标（立约/开工/协商/验收/交付）。
- 分工方案折叠面板：工单板，每行显示 工单/指派/类型/状态/redo，点行展开队员完整报告。
- 频道时间线：按成员着色的消息流（流式渲染），定向消息显示「→ @xxx」，用户与总管消息高亮。
- 交互：团队进行中发消息默认进频道（可 @ 点名）；「收队」按钮（立即终止并出未尽事项）；用户总管模式另有验收通过/打回按钮。
- 历史回放：仿 `buildRtReplayCard`（`static/app.js`）从消息 meta 重建折叠团队卡。
- 四期候选：独立「团队室」标签页（大屏消息板 + 工单看板；可实施规格见 §15）。

## 8. 存储与配置

- **一期**：团队全过程摘要落 assistant 消息 meta（仿 roundtable meta，长文截断），随会话持久化。
- **三期**：新表 `team_messages`（id, team_id, session_id, seq, from_member, to_member, msg_kind, task_ref, text, created_at，附 (team_id, seq) 索引）全量落库——编排器经构造注入的 message_sink 在每条频道消息定稿后逐条写入（未注入不落库，单测不受影响），建队分配唯一 team_id（uuid）随快照进 meta，会话删除不级联删频道史；`team.log` 按 team_id 回放全量（带会话归属校验，查无记录回空列表），前端团队卡回放两级容错（meta 带 team_id 先拉全量，拉不到退回一期截断 meta）。团队模板存 `~/.skysheep/teams.json`（`{"templates": [...]}`，条目字段 name / director_mode / director{provider, model} / members[{provider, model, name, persona}] / created_at；name 唯一键、同名保存即覆盖；仿 `subagents.json` 的坏文件容错），原子写走 `textio.write_text_atomic`。
- **用量**：逐成员 + 总管复用圆桌 `usage_rows` 模式入账 `usage_log`，归属当前会话。
- **`[team]` 配置段**（`config.py`，仿 `RoundtableConfig`）：

| 键 | 默认 | 说明 |
|---|---|---|
| `max_members` | 3（1~8） | 队员上限（不含总管） |
| `member_timeout_s` | 300 | 单成员单轮超时（队员干真活，比圆桌的 180 长） |
| `max_rounds` | 40 | 全局轮次上限（计数口径见 §13.6） |
| `redo_limit` | 2 | 单工单打回上限 |
| `stall_limit` | 2 | 成员停滞上限：连续 N 轮发言无新工具结果即停止自动唤醒、移交总管（§9） |

设置页配置卡三期已补（走四处：backend 读写 + dispatch 分支 + index.html 卡片 + app.js 回调）。

## 9. 防失控边界

| 边界 | 默认 | 触发后行为 |
|---|---|---|
| 全局轮次上限 `max_rounds` | 40 | 强制进入交付，未完成工单记未尽事项 |
| 单工单打回上限 `redo_limit` | 2 | 总管强制裁定（改派/降级/砍掉） |
| 单队员无进展发言上限 | 连续 2 次发言无新工具结果 | 强制移交总管处理 |
| 单条频道消息限长 | 2000 字 | 截断 + 全文落盘摘录投递 |
| 团队 token 预算 | 跟随会话每日预算 | 越线强制交付 |
| 单成员单轮超时 `member_timeout_s` | 300s | 该工单标 error，按失败隔离（沿圆桌先例） |

停机条件（任一即终态）：总管宣布交付 / 轮次耗尽 / 用户收队 / 预算越线。

## 11. 分阶段实施计划

### 一期 · 用户总管 MVP（已实施 2026-10-06）

- `core/team.py` 新模块：TeamChannel（频道）/ TeamTask+TeamBoard（工单板）/ TeamOrchestrator（用户总管编排循环：用户每条消息=总管指令，推进派工与频道，队员唤醒执行）。

## 13. 开放问题（实施前需决策）

1. **频道未读注入策略**：全量未读 vs「摘要 + 尾部 N 条」。一期先做全量裁剪（复用草稿预算思路），三期按实测 token 评估摘要化。
2. **AI 总管可否兼任队员领工单**：一、二期默认否（角色纯粹、避免自验收），后续视实践作为配置项放开。
3. **执行型工单是否进右面板「任务」列表**：建议不进（团队卡内自洽），避免与子代理任务簿双轨展示。
4. **team 与 roundtable 开关同轮互斥**：是，前端开关联动互斥，后端双参数同给时报错。
5. **团队进行中用户发无关闲聊**：一律进频道，由总管/用户自行处置，不做意图识别（保持行为可预期）。
6. **`max_rounds` 计数口径**（已决议 2026-10-06，随二期落地）：按**全局口径**计——总管轮、成员唤醒轮、小会（一场计 1 轮）合计计入 `rounds_used`，频道纯文本消息（广播、@闲聊等不唤醒任何人的消息）不计入。不按「成员唤醒轮数」计：AI 总管闭环里总管轮与小会同样是真实消耗（拆解、裁定、融合都要调模型），只数成员轮挡不住总管刷小会烧预算；防失控上限要罩住每一次模型调用。达到上限即强制交付，未完成工单记未尽事项（§9）。

## 14. 定时团队（无人值守）——四期可实施规格

> 2026-10-27 从 §11 四期候选「定时任务跑团队（HeadlessGate）」升格为可实施规格。口径：定时任务（cron）新增一种任务形态 `mode="team"`——到点以「团队模板」建队、AI 总管自动闭环跑一轮、交付《交付说明》后按定时任务既有路径收尾。全程无用户在场，安全基调是 §6.7 的 `HeadlessGate` 名单制 fail-closed（`security/gate.py:1728`），团队侧零新增放行：队员权限判定完全委托 HeadlessGate（`TeamMemberGate` 决策零改变的代理语义在无人值守下同样成立，`core/team.py:420`），无人值守三道防线照走——出站密钥 `_egress_pre_deny`、引擎主目录写入 `_write_hits_engine_home`、删除语义 `_write_is_actually_delete`（`security/gate.py:1740-1766`），名单放行之外一律 `pending.resolve(DENY)` fail-closed（`gate.py:1767-1770`）。
>
> 明确不做的：不接 `ChannelGate` 的审批档（`channels/gate.py` 的推卡等回复是给「有对话渠道」的场景，定时触发没有聊天窗口可推）；不改 `run_cron_task_core` 的收尾契约；不改 TeamOrchestrator（全部经既有注入面装配，模块层零改动）。

### 14.1 任务模型与入口（cron_add 新参数与校验）

**落点：`server/backend_parts/automation.py`（`cron_add` :817、`cron_update` :859）、`session/store.py`（cron_tasks 表 :131、`add_cron_task` :2698、`update_cron_task` :2723、迁移表 :394）。**

- 任务行新增两列：`mode TEXT NOT NULL DEFAULT 'agent'`、`team_template TEXT NOT NULL DEFAULT ''`。`_COLUMN_MIGRATIONS` 追加两行（沿 `("cron_tasks", "notify_channel …")` 同款，`store.py:394`），SCHEMA 版本 +1（`store.py:406` 起的版本注释惯例）；`add_cron_task` 加参数与 INSERT 列，`get_cron_task` 返回 dict 补两键（`mode` 以 bool 语义暴露给前端：`is_team = mode == "team"`）。`allowed_tools` 列复用不新增——team 模式下语义是「队员预授权名单」（§14.2），UI 与列不变。
- `cron_add` 新参数（WS 侧签名不变，params 扩展）：
  - `mode`：`"agent"`（缺省，既有行为）| `"team"`。白名单校验，非法值明示拒绝（沿 `schedule_type` 的入口校验姿态，`automation.py:823-825`）。
  - `team_template`：模板名，**只收引用不收内联名册**——名册内联进任务行会陈旧（换 Key、改人设都要逐任务重录），模板是三期已沉淀的复用单元（`core/team_store.py:90` TeamTemplateStore，`~/.skysheep/teams.json`），且前端建队浮层已有「从模板创建」语义。`mode="team"` 时必填，且必须能在 `self.team_templates`（backend.py:793 装配、:1539 启动装载）里按名命中，查无即 `RuntimeError`（沿 interval 校验的入口明示拒绝，`automation.py:826-832`）。
  - **模板资格校验**（定时触发的硬前提）：`director_mode == "ai"` 且 `director.provider` 非空。无人值守下没有用户当总管——user 总管模式每条消息都等用户指令（§2.1），到点只会空转。校验失败报「无人值守团队必须引用 AI 总管模板」。成员数不校验（模板条目本身不校验成员数，上限由应用时既有路径兜住，`team_store.py:56`）。
  - `prompt` 语义不变，即发给总管的首条指令（`run_auto_turn` 的 text）；`name`、调度参数、`notify_channel` 全部照旧。
- `cron_update`：`mode` 不允许改（agent↔team 互转意味着 allowed_tools 语义漂移，拒绝；换形态请删了重建）；`team_template` 可改，改时同款存在性 + AI 总管校验。
- `cron_run_now` / `cron_delete` / 归属校验 `_check_cron_ownership`（`automation.py:936`）零改动——团队任务就是一条普通 cron 任务行。

### 14.2 到点触发与装配（拉起 TeamOrchestrator）

**落点：`server/backend_parts/automation.py`（触发链 `_cron_pass` :757 → `_run_cron_task` :965 → `run_cron_task_core` :302 → `_execute_cron_turn` :995；新增 `_execute_cron_team_turn`）。**

触发链零改动：`_cron_pass` 的并发闸（`max_parallel_runs`，:762）、`spawn_bg` 后台派跑（:790）、`run_cron_task_core` 的库级 CAS 认领（:338-365）、单次硬超时（`timeout_s`，:391-401）、结果回写与终态推送（:416-442）对团队任务原样生效——团队轮只是「一次运行时间更长的 cron 运行」。改动只在 execute 注入点分流：`_execute_cron_turn` 开头按 `task["mode"] == "team"` 转入 `_execute_cron_team_turn(task)`，返回同构四元组 `(runtime, sid, stopped, facts)`（`facts` 的 denied 计数口径沿用 `make_progress_emit`，:1039）。

`_execute_cron_team_turn` 装配步骤（全部复用既有件）：

1. 前置检查同 `_execute_cron_turn`：`self.provider` 非空（:1003）、项目目录存在（:1008-1012）、`_cron_execution_context` 取归属项目与工作目录（:1013-1016）。
2. **模板二次读取**：按 `task["team_template"]` 在 `self.team_templates` 现查（入口校验只管创建时刻，模板可能后来被删，处置见 §14.5）。查无 → `RuntimeError("团队模板已不存在：…")`，由 `run_cron_task_core` 按 error 收尾。
3. 建独立会话：`store.create_session(cron_pid, title=f"⏰ {task['name']}")`（同 :1019，历史随运行累积、可审计）。
4. **权限门（唯一新增判定面，复用不改）**：`CronGate(allowed=task["allowed_tools"], store=self.store, project_id=cron_pid, working_dir=cron_workdir)`（`CronGate = HeadlessGate` 别名，`automation.py:123`）。两档配法与既有定时任务同一列同一 UI：
   - **只读档**：`allowed_tools` 空 → 只 READONLY 自动放行（且非引擎主目录写入），其余一律 DENY。适合调研/汇总/巡检类团队，执行型工单只能看不能写。
   - **白名单档**：`allowed_tools` 勾选（如 `fs.write_file`、`run_command`）→ 名单内放行（仍过删除语义与引擎主目录守卫），名单外 DENY。适合确需产出的团队；勾什么由用户在建任务时决定，界面上就是自动化页既有的「预授权工具」勾选。
5. 工具表：`self._build_full_registry(recorder)`（backend.py:1715，改动记录进同一 recorder，队员写的文件照常进检查点）。
6. 成员解析：`self._resolve_team_members([m.model_dump() for m in template.members])`（backend.py:3910——单个成员构建失败照常降级 `build_error` 入册，唤醒时按失败隔离呈现）。名册全员构建失败或模板 AI 总管构建失败（`_build_member_provider` 异常，backend.py:4042）→ 直接 `RuntimeError`，按失败收尾，不建一个注定空转的团队。
7. 编排器构造（`TeamOrchestrator`，注入面 `core/team.py:488-512`）：`emit` 用与 `_execute_cron_turn` 同款的收敛 emit（`cron_emit` :1042——流式/权限事件不进前端，只有工序进度 1 次/秒进工厂观战窗）；`working_dir=cron_workdir`；`registry` 同上；`gate=HeadlessGate 实例`（编排器内部经 `TeamMemberGate` 代理挂给成员，team.py:979——无人值守下代理转到的 pending 已被 HeadlessGate resolve(DENY)，不产生任何等待）；`cfg=self.cfg.team`；`session_id=sid`（写租约归属）；`hooks=self.hooks`、`mods=self.mods`（只能收紧，照 `_team_create` 的透传口径，backend.py:4062-4063）；`director_mode="ai"`、`director=DirectorSpec(provider_name, model, context_limit_tokens=…)`；`budget_check=self._team_budget_check()`（backend.py:3953）；`message_sink=self._team_message_sink(sid)`（backend.py:3975——频道消息照常全量落库，`team.log` 回放可用）。
8. 驱动闭环：`await orch.create_team(specs)`（team.py:662，TeamStarted 发出、team_id 分配）→ `await orch.run_auto_turn(task["prompt"])`（team.py:1442，AI 总管自动推进至终态或空闲）。**空闲续跑**：无人值守没有用户补消息，`run_auto_turn` 因「连续两轮无进展」空闲退出（team.py:1507-1524）而 `orch.finished is None` 时，投一条续跑指令再驱一轮：`run_auto_turn("（定时触发）请继续推进；若无法继续，请交付并记录未尽事项。")`，最多 `[team] cron_resume_limit` 次（默认 1，§14.6）；仍空闲则 `await orch.stop(reason="无人值守空闲收队")`（team.py:1771，产出未尽事项收队）。
9. **收尾适配**（`run_cron_task_core` 只读 `runtime.agent.history` 取最后一条 assistant 文本作结果摘要与 status 判定，:407-413）：终态后从 `orch.finished` 取《交付说明》（`TeamFinished.summary`），把它作为一条 assistant 消息 append 进会话（`store.append_message`，沿 CLI cron 的落库先例 cli/app.py:1184-1186），同时把任务指令 append 成 user 消息——会话 messages 表完整可审计；再返回一个轻量适配对象（`agent.history = [该 assistant 消息]`，模块级小类，注释说明 `run_cron_task_core` 只消费这一处）。这样 status 判定天然成立：任何终态（done / rounds_exhausted / budget_exhausted / aborted）都产出《交付说明》文本 → `last_text` 非空 → ok；终态原文（如 `rounds_exhausted`）写进 `last_result` 前缀与通知 body 注明，**不做错误化**——轮次耗尽/预算越线是 §9 设计内停机，不是故障。系统提示词不单独组装：总管与成员的提示词由编排器/Agent 自建，`compose_system_for` 这条 cron 专属路径只服务单 Agent 轮，团队轮不经过。

### 14.3 防失控上限沿用（零放松、零新码）

**落点：`config.py:121-136`（TeamConfig，不新增防失控字段）、`core/team.py:541-545`（构造取值）、`server/backend_parts/automation.py:987-993`（`_cron_timeout_s`）。**

| 边界 | 取值来源 | 说明 |
|---|---|---|
| 全局轮次 `max_rounds`（40） | `cfg.team` 经构造注入 | 总管轮/成员轮/小会计入口径见 §13.6，耗尽强制交付记未尽事项 |
| 打回上限 `redo_limit`（2） | 同上 | 超限强制裁定（改派/降级/砍掉） |
| 停滞上限 `stall_limit`（2） | 同上 | 成员停滞停止自动唤醒移交总管 |
| 单成员单轮超时 `member_timeout_s`（300） | 同上 | 该工单标 error 按失败隔离 |
| 成员上限 `max_members`（3） | 同上 | 模板超编在建队截断并 Notice（team.py:662 既有行为） |
| 团队 token 预算 | `_team_budget_check`（backend.py:3953） | 接既有每日预算 `usage_today`，越线强制交付 `budget_exhausted` |
| 单次运行硬超时 | `[factory] run_timeout_minutes`（automation.py:987） | `asyncio.timeout` 包住整个团队轮，超时按失败收尾释放占用位——团队轮在飞不豁免 |
| 并发上限 | `[factory] max_parallel_runs`（automation.py:762） | 一个团队任务占一个并发位，超出的到点任务排队 |
| 用量入账 | `_team_body` 的 usage_rows 同款口径 | 逐成员 + 总管入 `usage_log`，归属本次 cron 会话（由 team_emit 的归属接线承担，团队轮里事件不走 WS 但入账逻辑同构） |

设计原则：无人值守不设独立阈值——防失控上限只有一套（`[team]`），否则「定时团队」会成为上限口径的第二事实来源。

### 14.4 交付报告（格式、落库、可选渠道推送）

**落点：`server/backend_parts/automation.py`（`_execute_cron_team_turn` 收尾段；`cron_push_body` :195、`_fire_cron_push` :171）、`core/team.py:1829`（snapshot）。**

### 14.5 失败与重入

**落点：`server/backend_parts/automation.py`（`run_cron_task_core` :302 的既有收尾路径、`alert_repeated_failures` :220、`_cron_pass` :757）、`core/team_store.py:148`（模板删除）。**

- **上次没跑完又到点**：零新代码，三层既有机制完全罩得住团队轮——(1) 进程内在跑集合 `running` 判重（:351-352，force 也不重复触发）；(2) 库级 CAS 认领（:338-365，跨进程：应用内扫描与 Windows 计划任务拉起的 `cron run` 子进程同时到点时只有一方拿到执行权）；(3) 扫描循环的 skipped 去重记账（:766-779，长跑期间每 20 秒的扫描只记一枚「跳过」，不刷爆账本）。团队轮运行时间长（可能十几分钟），这三层正是为它这种形态准备的。
- **触发时团队模板已删**：不做级联——`team.template_remove`（backend.py:4606）不感知 cron 任务，允许悬空引用存在；代价在触发时结清：`_execute_cron_team_turn` 二次读取查无 → `RuntimeError` → `run_cron_task_core` 按 error 收尾（`last_status=error`、`last_result="团队模板已不存在：…"`、渠道推送 error），`alert_repeated_failures`（:220-299）按连续失败聚合提醒。`cron_update` 改引用时入口校验挡住手误。用户删模板时若想一起清任务，属前端提示优化，非本规格必需。
- **成员/总管模型不可用**（Key 失效、服务下线）：`_resolve_team_members` 降级 `build_error` 的成员照常入册，但**全员不可用或总管构建失败**时在装配期 raise（§14.2 第 6 步），按失败收尾——不建注定空转的团队烧轮次；部分成员不可用照既有失败隔离（工单标 error、总管改派）。
- **空闲收队**：续跑 `cron_resume_limit` 次仍空闲 → `stop()` 收队，《交付说明》带未尽事项，status 按 ok 记（有交付说明即有产出），终态文案注明。
- **应用重启**：cron 运行本无恢复语义（中断标 interrupted，下次到点照常触发）；团队会话沿 §3 重启处置先例——进行中的团队标注「已中断」，不自动恢复。无人值守团队本来就是「一次触发一次完整闭环」，没有跨触发的续跑需求。

### 15.3 与常驻团队（T3.2）的接口预留

常驻团队 = 跨会话存活的团队（§11 四期候选第三条）。团队室是「团队」从会话附件升级为一等实体的界面前提，本期按下述口径留缝，不给 T3.2 埋改约定的债：

1. **主轴已留双轨**：`team.room` 的 `team_id` 参数轴（15.2）——常驻团队落地后，团队室查询主轴从 `session_id` 切到 `team_id`，前端调用点只改参数、不改方法形状与返回形状。
2. **回放主轴已是 `team_id`**：`team_messages` 落库与 `team.log` 按 `team_id` 归组（三期已落地），会话删除不级联删频道史——团队搬家不丢频道，团队室的历史模式天然可迁移。
3. **归属校验的扩展点**：`team_log` 三态判定（`server/backend.py:4636-4642`）以「建队会话」为归属锚；常驻团队需要「团队归属」概念（成员会话集合或团队级 ACL）。本期不改宽任何校验（fail-closed 原样），T3.2 另立规则并配测试；扩展落地前 `team.room` 的 `team_id` 轴对非本会话团队一律拒绝，回放空态不可达即不可见。
4. **事件主轴后补**：五事件字段以 `events.py` 为契约（§7.1），常驻团队要求事件按 `team_id` 路由（同刻多团队）。本期前端按「当前会话单团队」假设消费、不预加字段；T3.2 给事件加 `team_id` 属向后兼容的加字段，`docs/无头运行协议.md` 同步。
5. **侧栏常驻入口后评**：团队随会话走时侧栏项空态率过高（15.1 入口选择的原因）；常驻后团队常在，届时加侧栏「团队」项（开团队室 + 活动团队数 badge）一并评估。

| 团队已终态（done / aborted / 轮次耗尽 / 预算越线） | 只读团队室：工单板无操作按钮、头部无收队/交付（同 `buildTeamReplayCard` 的 `card._finished` 口径，`static/app.js:4413`），成员带照常展示 |
| `team.log` 拉不到 / 库内零记录（旧版本团队没落过库） | 退回 `team.get` 快照的截断尾部渲染（两级容错既有口径，`static/app.js:4430` 注释块） |
| 后端不可达 / 请求失败 | 页签内错误行 +「重试」按钮（`loadTeamRoom(force)` 复用），不发全局 Notice |
| 页签在后台而团队在推进 | 不渲染，页签标题 badge 显示未读条数（见下） |

**未读与摘要化（开放问题 §13.1 的团队室侧）**：用户不是频道成员（`TeamChannel._cursors` 是成员游标，`core/team.py:172`），未读由前端自记——`last_seen_seq` 按 `team_id` 随 `saveUiPrefs` 既有机制落 `ui.json`，badge = `latest_seq − last_seen_seq`，进入页签即清零。**倾向（待议）**：摘要化分两面，成员注入侧的 `render_unread` 摘要化（省 token，§13.1 原题）与用户侧 badge（省注意力）动机不同，不绑定推进；团队室一期只做 badge + 进室清零，`render_unread` 维持一期全量裁剪（`core/team.py:281`），等 T3.2 常驻团队带来「长时间离场再回来」的真实场景后，两面一起评估。

### 15.5 开放问题（倾向均待议）

1. **AI 总管兼领工单**（§13.2）：团队室成员带会直观暴露「总管空闲而工单积压」的形态，是放开兼任的天然触发器；但一期团队室不动指派语义——可指派名单是 `TeamBoard.members`（不含 director，`core/team_board.py:123` 的 `add` 校验），兼任需把总管入名单、成员卡加「总管兼队员」双徽标、并解决自验收（总管领的工单谁验收）。**倾向（待议）**：维持默认否，团队室一期只做呈现不扩语义；若 T3.2 常驻团队实践中出现真实需求，走 `[team]` 配置项（默认关）放开，届时成员卡双徽标随成员带一并实施。
2. **频道未读摘要化**：见 15.4 末段——badge 先行，注入侧摘要化随 T3.2 评估。待议。
