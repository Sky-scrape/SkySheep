# 对抗模式设计（对抗性审查）

> 与「圆桌」（`core/roundtable.py`，多模型会诊融合）、「团队」（`core/team.py`，分工协作）
> 并列的第三种多模型协作形态：**对抗性审查（adversarial review）**。同一 AI 或不同 AI
> 分别承担 发现问题 → 核实真伪 → 给出方案 → 汇总报告 四种角色，用立场相反的
> 两次独立判断相互制衡，让误报在流水线里被物理过滤。本文是「对抗」功能的唯一概念来源。

## 1. 定位：圆桌 vs 团队 vs 对抗

| | 圆桌 | 团队 | 对抗 |
|---|---|---|---|
| 一句话 | 多模型并行作答，主席融合成更好的答案 | 多模型分工协作，总管派工验收交付 | 多模型攻防接力，终审产出一份审查报告 |
| 角色 | 成员（并列）+ 主席 | 总管 + 队员 | 发现者 → 调查者 → 建议者 + 裁判 |
| 角色关系 | 平等会诊 | 指挥链 | **流水线 + 对抗立场**（进攻方产出、防守方证伪） |
| 产出 | 融合答案（或 A/B 对比） | 交付说明 | 终审审查报告 + 问题清单（含裁决与方案） |
| 生命周期 | 单轮 | 会话级（多轮频道） | 单轮 |
| 适合 | 开放问题、方案比选 | 多步骤工程活 | 代码/方案/文档的**挑错与核实** |

对抗的核心理念与「让模型自己再检查一遍」的区别：自我检查时模型倾向于顺着
自己刚写的思路走（确认偏误）。对抗把「找问题」和「判真伪」拆成两个立场相反、
上下文隔离的独立调用，并给它们**不对称的激励**——发现者被鼓励过度报告
（宁滥勿缺），调查者被鼓励推翻（先假设不成立）——噪音靠流水线结构过滤，
而不是靠「请只报告严重问题」这类在复杂工程内容面前脆弱的提示词自律。

## 2. 角色体系（四角色）

| 角色 | 立场 | 职责 | 激励取向 |
|---|---|---|---|
| **发现者**（finder，进攻方） | 挑错 | 对被审内容穷尽式扫描：逻辑 Bug / 安全 / 性能 / 健壮性 / 设计，输出结构化问题清单（JSON） | 宁滥勿缺：每条候选都会被独立复核，误报会被推翻，漏报无法挽回 |
| **调查者**（investigator，防守方） | 证伪 | 逐条对抗验证：先假设不成立，再找证据（误读？外层兜底？实为设计？夸大？），给 confirmed / refuted / partial 裁决 | 推翻误报与确认真问题同等重要；但把真问题说成误报不可接受，没把握给 partial |
| **建议者**（advisor，修复方） | 给方案 | 只对成立/部分成立的问题给代码级/步骤级修复方案 + 风险 + 优先级 | 可执行优先，不许「建议优化」式空话 |
| **裁判**（judge，终审） | 收口 | 过滤噪音、按实际影响排序，产出面向用户的最终审查报告（Markdown，流式） | 删掉不值得处理的问题是职责，遗漏致命问题是失职 |

角色可由同一模型承担（角色差异来自系统提示词与阶段材料，不要求四个不同服务）：

- 输入框「协作」菜单选**对抗**后，弹层里为 发现者 / 调查者 / 建议者 三个角色
  **逐角色指定模型**（下拉，留空 = 自动挑选已配置 Key 的服务；同一模型可身兼
  数角——三个角色指同一个模型，正是「同一 AI 自我对抗」）；未指定的角色按序
  自动补位（members 带条目时未指定的从普通条目按序取，全空时取所有已配置服务）；
- **裁判缺省用当前主模型**（同圆桌主席口径：按会话三段解析，会话级换过模型的
  标签/分屏列由它自己的模型终审）；裁判与角色同服务是正常形态，不做回避。

## 3. 流水线（四阶段，事件流驱动）

一次对抗轮的事件序列（`events.py`，与圆桌同机制，backend 转 WS 帧广播）：

```
AdversarialStarted(roles=[四角色 {role, provider, model}])
  → AdversarialPhase(finder)
      AdversarialFindingProposed × N        （逐条候选问题，实时上卡）
  → AdversarialPhase(investigator, note="N 条候选问题待验证")
      AdversarialVerdict × M                （逐条裁决：confirmed/refuted/partial）
  → AdversarialPhase(advisor, note="K 条成立问题待给方案")   （无可解问题则跳过）
  → AdversarialPhase(judge, note="终审裁决")
      TextDelta × …                         （终审报告流进主对话，与圆桌融合同姿态）
  → AdversarialFinished(status=done|error|cancelled, summary=裁决统计)
```

流程约定：

- **发现/调查各合并为一次调用**：问题逐条编号进提示词、逐条裁决出 JSON
  （编号 `F-001` 是对齐键），成本与问题数解耦（同圆桌「一轮一次作答」的成本观）；
- 建议阶段只处理成立/部分成立的问题；被推翻的问题不出方案；
- 裁判报告直接流进主对话并作为**本轮正式助手消息落库**；问题清单（含裁决与
  方案）随消息的 `adversarial` 元数据持久化，历史回放时对抗卡可展开回看；
- 发现者空结果（高召回设定下一条没报）**短路**：不调后续三次调用，兜底报告
  如实标注来源（空结果本身就是结论，省一次调用）。

## 4. 上下文隔离（对抗有效性的前提）

四个阶段各自独立构建消息（角色系统提示词 + 会话上下文 + 本阶段材料），
阶段间不共享 history：调查者若先读到发现者的推理链，就会顺着对方的框架走，
对抗的价值恰恰在于**两套独立判断的碰撞**。共享的只有两样：会话上下文
（`history`，图片块剥除）与被审目标原文（本轮用户消息）。

## 5. 安全面（零新增）

沿圆桌先例：全程不传工具表（`tool_schemas=[]`）、不经过 PermissionGate——
纯文本协作，角色模型只读上下文与产出文本，无任何写文件/执行命令的通道。
被审目标是文本（本轮消息 + 会话上下文），不是工作区扫描（那是普通轮/子代理的事）。

## 6. 失败隔离与降级

单阶段失败不拖垮其余阶段（裁判照常出报告）：

| 阶段失败 | 处置 |
|---|---|
| 发现者 | 整场如实报错（status=error，没有问题清单，后续阶段无从谈起） |
| 调查者 | 涉事问题标 **pending（待定）**：不冒充成立也不冒充推翻，交裁判如实呈现 |
| 建议者 | 方案留空，裁决与终审报告照常 |
| 裁判 | backend 用中间结果拼一份如实的兜底报告（`degraded` 标记），已得的裁决不丢 |

瞬态错误（429/5xx 等）复用 `agent.py` 的判定与重试节奏（Notice 通告退避重试）；
JSON 解析失败追加一次**格式纠错**重试（把原始回复与纠错指令回喂给模型自己修），
再失败按上表降级。单角色调用超时 `[adversarial] role_timeout_s`（裁判自动加倍）。

## 7. 取消语义（与圆桌对齐）

`_run_text_turn` 把 CancelledError 收敛成 `error="cancelled"`（uncancel 消除悬挂
取消状态）：发现/调查阶段取消，已裁决结论保留；裁判阶段取消，已流出的部分
报告文本保留在 `outcome.report`，由 backend 落库——用户已经看到的内容不随
刷新消失。整场 status=cancelled，轮次按「已停止」收口。

## 8. 事件与 UI

- 输入区「协作」按钮的统一菜单四选一：不用协作 / 圆桌 / 团队 / 对抗（同一条
  消息只能选一种，选即生效、发送后复位）；对抗的设置弹层为三个角色逐行指定
  模型（下拉，留空 = 自动；选择即存）并说明裁判规则；偏好存 localStorage
  （`skysheep.adv.roles`，旧版勾选列表键自动迁移）；
- 对抗卡（聊天流内审查台）：标题「⚔ 对抗审查」+ 四阶段步进条（发现/调查/
  建议/裁判，随 AdversarialPhase 推进）+ 候选问题清单（严重度/类别/位置实时
  上卡，裁决徽记实时回填）；完成或报告就位后自动折叠，可展开回看；
- 终审报告气泡带「⚔ 对抗审查」徽标（红底，与圆桌紫/团队金区分），悬停显示
  角色名册；
- 历史回放：`message.adversarial` 元数据重建折叠的对抗卡（问题 + 裁决 + 方案）
  + 报告气泡 + 徽标；「重新生成」按原角色名册重跑（裁判仍用当前主模型）；
- 设置 · 对抗 卡：单场问题上限 / 单角色超时（`adversarial.get`/`adversarial.save`，
  读写均各端可用，改动只影响之后发起的对抗轮）。

## 9. 存储与配置

- 会话/消息：报告作为 assistant 消息入 `messages` 表（`adversarial` 元数据随
  JSON content 持久化）；无新表；
- 用量：按角色逐条写 `usage_log`（裁判记当前主模型名下），统计页与每日 token
  预算护栏看得见真实成本（对抗成本约「角色数 + 1」次调用）；
- `config.toml` 的 `[adversarial]` 段：`max_findings`（单场候选问题上限，1-100，
  默认 20，超出截断并提示）、`role_timeout_s`（单角色单次调用超时，≥10，默认 300）；
  走 `adversarial.get/save` 热生效。

## 10. 防失控边界

- 单场问题上限 `max_findings`（发现者超出按序截断并提示）——高召回设定必须
  有上限兜底，防止清单无限膨胀；
- 单角色超时（裁判加倍）+ 瞬态重试有界（同主循环 `MAX_STREAM_RETRIES`）；
- 单轮三态收口（done/error/cancelled），无跨轮状态——对抗是**无状态单轮**，
  不像团队有活动团队要收队；
- 与团队互斥：会话有进行中团队时消息进团队频道，对抗标志显式报错不静默吞
  （含排队轮交棒后的重验）；与圆桌三选一同轮互斥。

## 11. 与现有设施的复用对照

| 设施 | 复用方式 |
|---|---|
| `MemberSpec` / `_resolve_members` / `_build_member_provider` | 角色解析与 Provider 装配（chair 不回避） |
| `StreamDeltaMerger` | 裁判报告的 TextDelta 合并降帧；对抗事件非增量，冲刷语义自动保序 |
| `clip_draft` / `textio` 原子写 | 清单/描述限长与配置落盘 |
| `usage_log` + 预算护栏 + 预算告警 | 按角色入账，护栏与告警照常生效 |
| 排队（QueuedTurn） | 工作中发送的对抗轮照常排队，参数随队列传 |
| 检查点/会话落库 | 报告消息走轮末统一落库，无特殊路径 |

## 12. 非目标（当前不做）

- 不做工作区扫描型对抗（对整个仓库跑攻防）——那是普通轮 + 子代理的事；
  对抗只审「本轮送进来的内容」；
- 不做多轮辩论（发现者对裁决不服再反驳）——一期单程流水线；有分歧的问题
  用户可追问（上下文仍在会话里）；
- 不做对抗模板（同团队模板的沉淀路径，待有真实使用模式后再立项）；
- 渠道（飞书/微信）遥控对抗轮不在一期范围内（消息进渠道走普通轮）。
