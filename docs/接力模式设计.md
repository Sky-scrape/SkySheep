## 2. 实现单元与核心不变量

新增 core/relay.py（数据类型、预算、包校验、状态转换、纯文本模型调用）、server/backend_parts/relay.py（RelayMixin，后台编排、执行屏障、订阅、RPC）、server/static/app-relay.js（中文界面）、relaywindows.py（两个入口共享的桌面窗口控制器）。存储方法仍集中在 session/store.py；不另建数据库、不另起业务后端、不新建独立守护程序。

必须始终满足：

1. task 只有一个 active_session_id；只有 RUNNING 状态下它持有有效 generation 才能发起执行。PREPARING/RESTATING/VERIFYING 等状态，旧会话冻结且新会话无执行工具。
2. 交棒先撤销调度许可、等待已开始的动作及持久化结束，再准备新会话。交棒期间不得启动旧队列。CAS 成功之前，新会话绝不运行 Agent。
3. 窗口槽位、URL 参数、前端按钮和连接活动 session 均不是授权依据。每次模型执行入口及每个工具授权/执行前均检查任务状态、owner 和 generation。
4. 新会话继承项目、模型、原权限档位；PermissionGate 及默认确认照常生效。尚未决的权限请求不迁移、不替用户批准；本代决定不能授权下一代工具。
5. 任何不确定的副作用、存储失败或过期回调都不能产生新 owner 的执行。历史与交接失败记录保留；停止、重启不自动重放工具。

默认每个项目最多一个非终态接力任务，同时禁止该项目启动另一个会改动同一工作区的协作执行。启动接力前检查现有运行轮、排队轮、后台进程、子代理与团队，提示先停止并等待结束。接力运行中其他会话可查看与普通纯文本阅读，但对项目执行类入口统一阻断；只读浏览不等于另开工具 Agent。此约束减少无法追踪的同项目并发，不改变其他项目的工作方式。

## 3. 状态机及命令语义

| 状态 | 所有者可执行 | 转换与退出条件 |
|---|---|---|
| RUNNING | 仅 active_session_id + generation | 用户目标尚未完成则持续轮次；目标完成进入 COMPLETED；手动/占用触发进入 PAUSE_REQUESTED |
| PAUSE_REQUESTED | 仅允许已经开始的动作收尾 | 禁止新模型请求、工具批次、旧队列；已发出的整批工具必须得到真实结果或明确错误，不抛弃 tool_use；静止且持久化成功进入 PREPARING |
| PREPARING | 无 | 旧会话无工具生成结构化包，服务端校验并保存，创建下一槽全新会话；进入 RESTATING |
| RESTATING | 无 | 新会话无工具复述，成功进入 VERIFYING |
| VERIFYING | 无 | 旧会话无工具核验；拒绝则有限补包回 PREPARING，通过进入 COMMITTING |
| COMMITTING | 无 | SQLite CAS 原子提交 owner、generation、槽位链与交接结果；提交成功进入 RUNNING（新 owner），失败进入 PAUSED |
| PAUSED | 无 | 有界重试用尽、预算不足、静止超时、provider/存储故障；显式 retry/resume/takeover/stop |
| INTERRUPTED | 无 | 启动恢复所有非终态；显式核对副作用后 resume/takeover/stop |
| STOPPING | 无新动作 | 用户停止时立即禁新执行，等待实际动作结束；未知副作用仍显示 STOPPING 并禁止复用工作区执行 |
| STOPPED / COMPLETED | 无 | 终态，保留历史；新任务需要显式创建 |

设计中的阶段枚举使用小写持久化值；上表大写用于便于阅读。所有状态变更附递增 revision，generation 仅在授予新执行代际或显式恢复时增加。失败保留 active_session_id 作为最后执行者身份，但非 RUNNING 时不构成可执行许可。

自动持续：执行 Agent 正常完成一轮后，后端以纯文本完成判断得到 completed 或 continue 和下一步；非完成时将续行指令写入可追踪消息后启动下一轮，不等用户重新发消息。该判断无工具，有格式校验和超时；无法判断则 PAUSED。复用 Agent 每轮迭代上限，另设任务 max_turns 默认 100（可编辑），达到时暂停，不偷偷从头再跑。只有最终判定完成才 COMPLETED；同一响应不能既交棒又宣布完成。

手动交接/停止可在任意阶段请求；stop 优先于 handoff/commit，串行任务锁保证提交时重新检查 stop 标记。takeover 表示停止自动推进，由用户选择“继续当前会话”或“改用当前候选会话”；候选未通过核验时不能直接授权，需重新完成复述核验。旧会话已经转出后不允许重新成为执行者，需新会话重新接棒。resume 是显式恢复当前 owner 的新 generation，不自动重放最后工具。

交接失败默认暂停，不自动回旧会话执行。retry 复用失败 handoff 的新 attempt，在本次上限内重做；用户显式发起新的尝试须保留前一次记录，不能隐藏无限自动重试。

## 4. 安全边界、并发与副作用收敛

Agent 新增可选 async boundary 回调，在 agent.py:411 压缩前、每个模型请求前及完整工具结果批次后检查；普通模式回调为空。先到达安全边界后正常结束本轮，TurnFinished.stop_reason=relay_handoff；不以 CancelledError 作为成功交接信号。轮首 checks 必须早于 mods/hooks 可执行回调，交接协商全程不调用 Agent、mods、hooks、工具注册表。

后端对直接 send、regenerate、重试、队列消费、内部自动续行、会话恢复执行，以及独立工具/任务启动 RPC 统一调用 require_relay_execution(project_id, session_id, generation)。接力会话关闭后绑定仍保留，不能通过传 relay=false 退化普通执行。前端四模式清空互斥只是交互，服务端也强制四选一并检查项目活动任务。归属验证复用 _get_owned_session；接力一期控制 RPC 为 local_only，远程连接不能以 task_id 读取其他会话内容或扩大权限。

任务管理器持强引用，唯一 task lock 串行阶段转换；执行许可在一个工具真实完成以前一直登记为 in-flight。取消等待方不得撤销真实动作记录；用独立 worker task + shield/finally 完成登记归还。PAUSE_REQUESTED 时不再启动下一批工具；当前已输出的工具批次正常按原门控完成（允许用户 deny），然后持久化。边界到达需要同时满足：无模型执行流、无未决权限、无 in-flight 工具、无未结子任务/进程、无未完成持久化、旧队列被冻结。

现有 run_command 经 to_thread 运行，取消 asyncio 不能证明命令停止（shell.py:636-653）。实施不能只统计 runtime.run_task：

- 接力执行中拒绝 background=true、后台子代理、任务/流水线/日程等可派生自主执行的工具参数或独立 RPC；明确中文错误可让模型改为前台执行。不能只按 Safety.READONLY 筛选。
- 前台 shell 登记进程及子进程生命周期，复用现有进程管理；运行 worker 的完成通知不可随请求取消而丢失。命令主进程退出仍有已登记子进程时不能交棒；用户可结束进程树后重试。接力不承诺迁移常驻 dev server。
- 启动命令时采用现有可用的进程树约束/管理能力；平台不能证明已启动进程树静止、命令脱离跟踪或工具报告外部异步执行时，以 external_effects_unknown 暂停，不得把“进程号消失”当成所有副作用停止。UI 提供具体任务/进程原因及人工核对后恢复；后端不默默杀进程或跳过屏障。不能靠 shell 文本黑名单证明静止。
- 接力开始前已经运行的任务也属于屏障检查，不能漏掉项目 ctx.tasks。普通 MCP 调用同样计入 in-flight；返回了外部后台任务句柄则标记未结，不能凭返回文本自动完成。无法证明终止的动作需要人工核对，接棒不会绕过这个限制。

stop 首先禁新动作并使未决权限按 deny 收尾，再请求现有取消能力，等待真实 workers/进程和持久化。达到 settle_timeout 仍未结束，保留 STOPPING 或 PAUSED 并显示原因；不授权 B，也不称已安全停止。强杀进程、清理文件仍需现有权限流程。本模式不能彻底判定任意外部工具的远端副作用，保守暂停与人工核对是明确的产品行为。

## 5. 上下文阈值、预算与交接包

C 取当前会话实际模型 effective_context_limit，U 取 used_context_tokens()，累计 total_in_tokens 不参与。估算须补足 provider 未计入历史估算的工具 schema 与 system 开销，并在每次 ProviderDone 更新真实输入下限（调查 agent.py:482）。配置 handoff_ratio 默认 0.75，范围 0.5–0.9；reserve_tokens 默认 8192，recent_tokens 默认 4096。实际 R=max(配置 reserve，包生成与核验最小输入/输出预算)，阈值 T=min(floor(C*ratio), C-R)。容量不支持最低可用预算则启动失败并解释，不能把负 T 当无限交接。

启动时校验输出上限与输入余量；在每次下一模型请求前计算 U >= T。一次工具返回可能使 U 突增，因此每次工具结果批次后检查。若下一次模型调用预估输入+输出将超 C，立即进入交接准备或 PAUSED，不先发超限请求。普通自动压缩在接力判断之后；只在准备包时作为降噪辅助手段，不能压掉交接触发。新会话预算检查不通过不能提交，防 A/B 空转。

生成包的旧会话请求采用受预算约束的历史视图，保留明确目标/用户约束、最近完整工具链和路径/验证摘要，必要时复用 compact_history 的摘要能力及 context.py 的估算、配对切分，不改写已持久历史。不能把压缩摘要本身当交接记录。近期对话按 tokens 裁剪，不按字符或任意条数；图片与大工具结果转为引用/摘要并写 omitted 标记，保留原消息 seq 供追溯；不把隐藏思考链作为交接材料。

HandoffPacket v1 固定结构：schema_version、task_id、handoff_id、attempt、from/to session、from/to slot、expected_generation、created_at、user_goal、completed[]、remaining[]、constraints[]、decisions[]、artifacts[{path,description}]、validations[{command,result,status,evidence_seq}]、next_steps[]、risks[]、recent_messages[]、source_seq_range、omissions[]、budget{capacity,estimated_input,reserved_output,recent_tokens}。validation status 只取 passed/failed/not_run/unknown；不能把模型自述当作实际运行结果。包是本地数据，不自动上传文件、不拉取外部 URL。

服务端做类型、必填、长度、ID/项目、状态和预算校验；goal、remaining/完成说明、constraints、next_steps 必须明确（可显式为空但必须说明）。路径是资料而非执行指令，验证命令只展示，不自动运行。source_seq_range、文件与检查结果来自真实事件/消息引用，模型补充无证据则标 unknown。用户在交接中插话作为 task instructions 持久化；协商快照之后出现的指令使包失效，需重新包含，CAS 同时检查 instruction_revision。

## 6. 复述、核验与有限重试

PREPARING、RESTATING、VERIFYING 均直接 provider.stream(messages, [])，不是 plan_mode，也不启动 Agent；任何工具增量记为协议错误并中止此次协商，绝不 dispatch。provider 若具有独立内置执行工具选项，同样显式关闭，否则拒绝用于协商。包与对话以数据块传入，系统约束声明不能当作授权。

B 输出 Restatement v1：goal、completed、remaining、constraints、next_steps、uncertainties、packet_id/hash。A 依据旧会话预算视图与包核验，输出 verdict=pass/reject，missing[]、corrections[]、reason。服务端还检查 hash、目标与关键字段覆盖、大小及未解决 uncertainty；A 的 pass 不能覆盖结构校验失败。通过后将包、复述、核验作为类型化交接记录保存，并给新会话注入明确来源说明；不伪装用户消息。

拒绝时 A 根据缺漏补包，B 重新复述，A 再验。默认 max_attempts=3（含首次），单阶段 timeout_seconds=90，总交接预算 timeout 默认 360 秒，settle_timeout=120 秒；所有值经范围校验。provider 格式错误计入同一上限，不另套无限 provider retry。超时/上限/stop 进入暂停或停止状态，保存所有尝试、失败原因与半截文本。迟到返回携带 attempt/generation，作废不触发移交。

核验通过后才执行提交；提交前再次检查旧执行者静止、持久化无失败、无新用户约束、无停止请求及预算足够。提交后的续行以 handoff_id 派生唯一 continuation_id，防重复通知造成两次启动。进程在提交后但启动前退出，重启保持 INTERRUPTED，不自动补跑。

## 7. 数据库存储与兼容

使用现有 skysheep.db，通过 connect 初始化的幂等 CREATE TABLE IF NOT EXISTS 增量迁移，不改已有 messages/FTS 语义、不重写历史、不改应用版本。新增：

- relay_tasks：id PK、project_id、state、active_session_id、active_slot、generation、revision、instruction_revision、goal、model_snapshot_json、permission_snapshot_json、config_snapshot_json、error_json、created_at、updated_at。
- relay_sessions：task_id、session_id（唯一）、slot、ordinal、predecessor_session_id、role/status；UNIQUE(task_id,ordinal)。保留每一代绑定，交接失败候选也记录。
- relay_handoffs：id PK、task_id、from_session_id、to_session_id、expected_generation、attempt、status、packet_json、restatement_json、verification_json、failure_json、continuation_id UNIQUE、created_at、updated_at。
- relay_actions：task_id、request_id、action、result_json；UNIQUE(task_id,request_id)，用于控制命令幂等。用户插话可用类型化 task instruction 记录（单独 relay_instructions 表），不能仅写 UI 内存。

针对共享连接交错提交，采用 Store 内专用 relay_write_transaction：通过一条独立短生命周期 SQLite 写连接 BEGIN IMMEDIATE → 参数化 SQL → COMMIT/ROLLBACK，busy_timeout 有界；与已有 _db 不共享事务。迁移只在主 connect 完成后进行。事务内不能 await provider、窗口、持久化 API 或调用会自行 commit 的 create_session/append_message。候选 session 的创建可在独立事务中与 relay_sessions 插入一起完成；创建成功不授予执行权。

commit_handoff 一次事务校验 task.state=committing、expected owner/generation/revision/instruction_revision、handoff.status=verified；UPDATE task 设置新 owner/slot、generation+1、revision+1、running；UPDATE 旧/新 relay_sessions 状态；UPDATE handoff committed 及唯一 continuation_id，必要通知标记同次提交。CAS rowcount != 1 回滚，不凭内存设置 owner。提交消息前先完成并确认 _persist_turn 成功；这不是跨连接原子消息写入，设计不作此承诺。失败保持冻结。

全部外部字段使用 SQL 参数绑定，表名与字段名为静态代码，不把用户输入拼接、format 或 f-string 到 SQL。接力本身不新增服务端外部 URL 请求；后续若引入，必须沿用已有 SSRF 防护，仅 http/https，逐跳校验公网 host 并拒绝本机、环回、私有与保留地址，不因同源窗口功能放宽联网接口。

数据库是恢复依据；内存锁保证同进程调度串行，CAS 防过期事件/多连接。增加按规范化 store.path 的后端进程独占锁（Windows 文件锁与跨平台文件锁兜底），使 desktop 与 CLI 同时指向同一 HOME 时第二个后端失败并说明；桌面单实例互斥不涵盖 CLI。独占锁不能靠 PID 文件存在判断，也不自动抢占活进程。否则只做 SQLite CAS 无法阻止两个进程同时恢复旧 owner。

启动时持锁后将所有非终态转 interrupted，generation/revision 增加使所有旧 token 作废，加载历史、包、未结动作说明。要求用户核对外部任务、最近命令和文件检查点，再显式 resume；不因前端自动重连恢复执行。导入备份/替换 store 时先冻结与收敛接力，重建连接和锁后按重启恢复，不复用旧内存 owner。

会话删除/清项目/恢复备份操作必须先停止关联接力并收敛；活动链禁止单独删除。终态删除链需明确确认并说明关联历史；本次实现可直接拒绝逐段删除且提供只读历史，不做级联隐删。老数据库无接力表时正常创建空表，旧配置无 [relay] 时使用默认值。

## 8. WS 契约、事件与配置

统一响应沿用 {id,result/error}；错误含稳定 code、中文 message、task_id/state/revision，事件含 task_id/session_id/slot/generation/revision，不把展示窗口当权限信息。控制命令必须带 request_id、expected_revision，重复 request_id 返回已存结果，不重复创建会话；过期 revision 返回 relay_conflict 和快照。

| 方法 | 参数与行为 |
|---|---|
| relay.start | `session_id`、`goal`、`workflow`、`request_id`、`expected_revision=0`；校验项目/模式/后台状态，建立任务与初始节点；不默认假定 A 执行、B 待命 |
| relay.get | `task_id`；快照含工作流 revision、节点/边状态、A/B 当前 session、active owner、阶段、阈值与阻塞原因 |
| relay.subscribe / unsubscribe | `task_id`；按连接订阅完整任务事件，不更改全局活动会话；订阅先快照再按 revision 对齐 |
| relay.handoff | `task_id`、`from_node`、`to_node`、`request_id`、`expected_revision`；只请求安全边界，不直接 cancel、授予权限或切 owner |
| relay.node.approve | 对需要用户确认的节点或连线批准一次具体 `plan_id`/`revision`，不能批准未来未生成的方案 |
| relay.pause / resume | 暂停自动推进；恢复需确认副作用核对状态，不能绕过屏障 |
| relay.retry | 指定失败节点/边或 handoff，显式重试；仍有次数与超时上限 |
| relay.stop / takeover | 记录停止/接管意图，返回收敛中快照；只有屏障完成才显示已停止/可继续 |
| relay.instruct | 持久化用户插话，递增 `instruction_revision`；执行轮首注入或使相关节点方案失效 |
| relaycfg.get / save | 读回/编辑/校验屏幕槽位、节点、连线和循环约束，`update_config_section` 后 `load_config` 热更新并返回有效值 |
| relay.window.open / focus / layout | 仅本机调用已登记桌面控制器，指定 `task_id`/`slot`；无任意 URL/命令/路径入参 |

事件最小集 relay_state、relay_handoff（phase/attempt）、relay_session_bound、relay_error、relay_context；运行流式事件补 task/session/slot 标识并广播给订阅者。主业务运行使用任务级 emit，不绑定发起 RPC 的连接；所有增量先经 StreamDeltaMerger，非增量阶段事件前 flush；正常/取消/异常收尾都 flush。断线重连 relay.get+历史同步，不重放执行。多连接不各启动 driver。

配置字段：handoff_ratio、reserve_tokens、recent_tokens、max_attempts、phase_timeout_seconds、handoff_timeout_seconds、settle_timeout_seconds、max_turns、max_no_progress、max_workflow_retries、window_layout（auto/dual/single）、A/B 屏幕偏好、槽位节点配置、工作流边、循环上限、汇合策略、用户确认策略、终止条件。节点配置至少包含 role、model、capabilities、execution_mode、context_scope、handoff_policy、completion_signal、output_subscription。默认提供“ A 执行 → B 复核规划 → A 执行”模板，但不将其写死为系统行为；保存配置时必须验证图无未定义目标、执行节点有能力边界、循环有上限且存在终止条件。默认沿用当前模型；更换模型/容量只允许暂停后显式应用并重新预算。超时/预算/轮次等保存后对下一安全边界/下一次协商热生效，已开始协商的配置快照不在途中被改变；显示“本次工作流使用保存前设置”。配置方法 local_only，执行权限仍由现有 PermissionGate 决定。

前端在四模式入口加入接力；发送使用独立 relay.start 或 relay.instruct，普通 chat.send 的 relay 标记若保留只作适配转发，不能创建第二条编排路径。UI 显示执行者/待接棒、固定槽位 A/B、实际占用/容量、交接阶段、剩余重试、阻塞原因、历史链，按钮均对应真实 RPC。协商正文用 textContent/现有安全渲染，不将模型 JSON 插成 HTML。

## 8.1 主副屏 AB 方案定稿（用户可编排口径）

本节覆盖参考文档中“旧窗口 A → 新窗口 B”的差异。SkySheep 的 A/B 首先是两个**固定物理展示槽位**，不是预先写死的执行者和规划者：

| 名称 | 固定含义 | 默认布局 | 可配置内容 |
|---|---|---|---|
| A 槽位 | 用户指定的主协作窗口 | 主显示器工作区 | 模型、角色、可用工具、是否可执行、输入/输出订阅 |
| B 槽位 | 用户指定的副协作窗口 | 选定的副显示器工作区 | 模型、角色、可用工具、是否可执行、输入/输出订阅 |

默认推荐 A 主屏执行、B 副屏规划，但这只是模板，不是系统约束。用户可以配置为：A 执行/B 复核、A 规划/B 执行、A 与 B 分工执行不同子任务、A/B 互相评审、单向流水线、双向讨论后由用户选择，或两个窗口只读观察同一任务。

窗口位置、窗口标题前缀和槽位身份不随交接交换。变化的是每个槽位绑定的 session、角色和协作代际。`A1 → B1 → A2 → B2` 只是默认的交替模板；实际流程由用户配置的工作流图决定，例如 `A → B → A`、`A → B → C`（未来扩展）、`A ↔ B`、`A/B 并行 → 用户裁决`。无论采用哪种流程，只有后端授予执行许可的 session 才能调用执行型工具。

### 用户可配置的协作模型

每个槽位应独立配置以下字段：

- `role`：执行、规划、复核、研究、汇总、裁判、观察或自定义角色；
- `model`：使用的模型服务和模型名；
- `capabilities`：允许的工具集合，按只读、项目写入、命令、网络、子代理等能力分层；
- `execution_mode`：`readonly`、`propose`、`execute`、`approve_then_execute`；
- `context_scope`：完整任务、指定会话、指定文件、上一轮报告或用户选定内容；
- `handoff_policy`：自动发送、等待用户确认、满足条件后发送；
- `completion_signal`：模型结构化结论、测试通过、文件变更、用户确认或组合条件；
- `output_subscription`：接收另一槽位的全部消息、结构化报告、工具结果摘要或仅接收用户消息。

用户通过工作流编辑器配置节点和连线，而不是让前端根据窗口位置猜测职责。每条连线都应声明输入格式、触发条件、是否需要用户确认、目标槽位和失败处理。自然语言方案可以作为节点内容，但不能替代结构化的状态和授权。

### 可编排但不可绕过的底线

1. 槽位职责可以自由配置，**执行许可不能自由伪造**。后端为每个任务维护唯一的 active owner；允许并行时也必须为每个可写工作区建立明确的 ownership/lease，禁止两个节点无协调地写同一文件。
2. 用户可以允许 A、B 都执行，但每次执行仍经过 `PermissionGate`，并由工作区写租约、任务 generation 和工作流 revision 约束；“B 生成的方案”或“A 的上一轮授权”都不能自动放大权限。
3. 用户可以设置自动循环，但必须配置最大轮数、预算、连续无进展上限、失败重试上限和停止条件；任何未定义终止条件的循环都拒绝启动。
4. 用户可在任意节点暂停、停止、接管、改派或修改连线。配置修改从下一安全边界生效，正在执行的节点使用启动时的工作流快照。
5. 窗口可见性、焦点、屏幕位置和槽位名称不是权限依据。关闭窗口只影响展示订阅；无法证明副作用已经收敛时，工作流暂停而不是自动跳过。

### 屏幕选择规则

1. 启动时重新枚举显示器，优先把系统标记的主显示器绑定 A；不能取得主显示器标记时，使用包含系统工作区原点 `(0, 0)` 的屏幕，再退回枚举第一块屏幕。
2. B 从剩余屏幕中选择。优先级为：用户保存的稳定屏幕偏好、上次绑定的屏幕指纹、与 A 的工作区距离最近且不重叠的屏幕、枚举顺序。屏幕指纹只作为偏好，不作为永久设备身份，不能因为换显示器而把 B 放到屏幕外。
3. 屏幕指纹至少包含显示器工作区逻辑矩形、物理尺寸/缩放信息（可取得时）和相对排列方向；不得把临时 `screen index` 当持久 ID。
4. A/B 均使用工作区而不是整块屏幕，避开任务栏。所有保存和定位坐标使用 pywebview 逻辑像素；Win32 物理像素只在采集/换算边界出现一次。
5. 两块屏幕不足两个 `980×640` 最小窗口时，不强行缩放或放到屏外：保留 A 在主屏，B 改为同页分屏或待命未打开，并在 UI 明确显示降级原因。
6. 副屏拔出、禁用、分辨率或缩放变化时，A 仍优先留在当前主屏；B 重新解析到当前可用的非 A 屏。找不到第二块屏时不改变执行权，只关闭/折叠 B 的展示并保持任务继续。

### 通用节点交接时序

1. 工作流图中的当前节点达到完成条件、资源阈值、用户指定触发器或手动“发送给下一节点”后，后端冻结该节点的新执行。
2. 后端等待工具、子进程、MCP 调用、权限请求和持久化达到安全边界，生成带 `from_slot`、`to_slot`、`workflow_revision`、`node_generation` 的结构化交接包。
3. 目标槽位加载交接包，并按该节点配置执行：只读复述、独立研究、方案生成、复核、用户确认，或经过授权的执行。默认协商节点无工具；需要执行的节点必须单独声明 `execution_mode` 并重新经过权限门。
4. 若工作流边声明需要核验，指定的复核节点或用户进行核验；核验失败回到当前节点或进入配置的失败分支，不授予目标节点额外权限。
5. 后端以 CAS 提交节点状态、工作流 revision、输入输出摘要和下一节点执行许可。提交成功后，目标节点才可启动；提交失败则保持冻结并进入暂停。
6. 后续节点按工作流图继续，而不是默认 A/B 交替。允许循环、并行和汇合，但每次跳转都必须有可追溯的边、代际和终止条件。

### 与参考 AB 流程的明确差异

- 不使用分享链接、IndexedDB 抓取、DOM 读取、自动点击或外部 watchdog 作为交接依据；这些只能作为未来兼容层，不能成为核心链路。
- 不关闭旧槽位窗口，也不把副屏窗口移动到主屏。窗口生命周期由同一进程的 `RelayWindowController` 管理，任务状态由后端数据库和 generation 管理。
- “B 窗口已打开”不等于“B 已接棒”；只有复述、核验、CAS 三步全部成功，UI 才显示“B 正在执行”。
- 窗口不可见、被用户关闭、浏览器弹窗被拦截都不改变执行权，也不能触发自动重试工具；只产生展示告警和可恢复的订阅状态。

### 用户可见状态

双屏模式下，两个窗口顶部都显示固定槽位标识（`A · 主屏` / `B · 副屏`）、当前 session 代际、用户配置的角色、当前节点、执行/待命/核验状态和任务编号。交接中显示“当前节点已冻结”“目标节点处理中”“等待核验”“已提交”等与实际工作流阶段对应的状态，避免用户把“新窗口出现”误认为任务已经切换。用户可以在任一窗口发起暂停、停止、查看交接历史；只有通过后端 owner/generation/workflow revision 校验的控制请求才会生效。

## 9. 真实窗口、显示器与降级

新增 RelayWindowController，由 desktop.py 与 cli/app.py 各自启动时注入同一后端实例，仅接收任务/槽位布局请求。通过 pywebview 支持的 GUI 调度路径在同一进程动态 create_window，共用既有服务器 URL 与同一应用 profile，不再启动第二份服务。每个窗口各有 FilePicker 绑定、主题/麦克风/关闭钩子。若运行平台不支持动态原生创建，接口返回 browser/single 可用能力而不是虚报已打开。

现有主窗口作为 A；启动接力时按用户工作流创建或绑定 B 窗口。目标节点 session 在交接准备中绑定到指定槽位，是否只读、是否执行以及何时启动均由节点配置决定；旧 session 进入历史，不能把旧历史列表当作新 session 的当前上下文。任务映射更新由 `relay_session_bound` 驱动。URL 只携带受控 `task_id`/`slot` 作为展示绑定（校验归属），不含 token、cookie、profile 路径或公开分享链接。

auto 布局：两块屏幕时 A 放选定主屏工作区，B 放另屏；只有一块时优先同页 A/B 并排（复用已有 split 面板但两侧按 task 槽位绑定），可切两真实窗口。小屏不足两个现有 980px 最小窗口时不要强行并排出屏；可重叠窗口由用户切换，界面说明当前布局。交接逻辑不等窗口加载成功，窗口不可见不改变执行权，但 UI 清楚报告展示失败。

window_state.json 扩展 version=2、normal 原单窗口几何、relay.slots.A/B 各自屏幕偏好与几何。保留旧 load_state/save_state 对普通窗口兼容，增加专用接口；所有写集中控制器串行合并并走 write_text_atomic，不能两个关闭钩子各覆盖对方。显示器键是偏好，不保证设备永远相同；找不到时按现存屏幕回退。几何采用 pywebview 逻辑像素，不把 Win32 物理像素直接传入；Windows 采集复用现有 DPI 换算（所附调查 desktop.py:591-644）。

窗口显示/布局按钮/获得焦点时重枚举屏幕，并用低频桌面能力检查屏幕集合变化（这是同进程展示检查，不是业务看门狗）。副屏拔出/分辨率变化后用 resolve_geometry 重新夹紧到当前可见工作区；混合缩放按目标屏 DPI 换算后定位，保留 A/B 身份不交换角色。定位失败给出“恢复到当前屏幕”按钮。保存几何失效走可见默认值，不让 B 永久在屏外。

关闭 B 只取消展示订阅，任务按后端继续，A 显示 B 未打开且可恢复；关闭 A 但 B 在时不停止后端，B 提供所有控制。最后一个原生窗口关闭前冻结新执行并触发正常停止/收敛；等待超时仍记录 interrupted/未结动作，不假称安全退出。浏览器模式由既有服务生命周期托管，关闭标签不是 stop；UI 显示“关闭页面不会停止任务”。

--browser 无原生句柄：提供同页真实 A/B 会话并排，以及用户点击“打开 B 窗口”使用同源受控 URL；受到弹窗拦截时维持并排并显示原因。window.open 成功只代表展示请求，必须收到 B 订阅确认才显示已连接。浏览器不能可靠定位物理副屏，界面提示手动拖动；不得宣称自动双屏。不能通过 app.open_external 引入任意 URL。

## 12. 必须真实跑通的场景

| 场景 | 断言与证据 |
|---|---|
| 默认双屏模板 | fake provider 执行 A → B 复核并生成方案 → A 执行；每次节点输入、方案版本、执行结果和终止条件可追溯；A/B 窗口位置不换，最终文件与检查结果正确 |
| 自定义单向流水线 | 配置 A → B，A 只读报告、B 执行；验证职责和工具权限按配置生效，不因槽位名称改变 |
| 双向评审循环 | 配置 A ↔ B，设置最大轮数、无进展上限和用户确认分支；达到任一条件后停止，不能无限自循环 |
| 并行与汇合 | A/B 并行只读研究后汇合到用户裁决或指定执行节点；同一文件写租约冲突时阻塞，不允许无协调覆盖 |
| 节点硬只读 | 规划/复核节点故意返回 shell、memory、MCP 工具调用；工具执行计数为零，文件与状态无改变；fake provider 记录 `tools=[]` |
| 方案审批与失效 | 用户只批准当前 `plan_id`/revision；用户插话、文件冲突或工作流改版后旧方案失效，迟到方案不得执行 |
| 交接拒绝与上限 | 节点首次缺约束，按配置回退或补方案；持续拒绝恰好达到上限后暂停，迟到 pass 不提交 |
| 权限 | A 写需确认；B 接棒后仍需相同权限，不复制未决 allow；错误 generation、旧 session、regenerate/队列/独立任务 RPC 均不能启动写入 |

## 15. 语义修订（2026-10-18）：主副屏交替

用户明确了接力的真实用法：**发布方案 → 执行 → 反馈这类需要两个分工不同的
Agent 交替推进的任务**。此前的「无工具串行 A/B 模型槽位」实现保留在后端
（`relay.*` 旧 RPC 与三张表仍在），但界面已全部切到下面这套语义。

- **主屏 = 当前会话，副屏 = 绑定的独立会话**。点左侧「接力」时：右侧看板打开，
  同时通过 `openSplitPane` 把副屏会话打开在聊天右侧的分栏里（同页并排，不宣称
  物理双屏）。副屏会话标题固定 `接力 · 副屏`，同一项目里没有消息的同名会话会被
  复用，避免每点一次就多一条空会话。
- **右侧看板**：总任务、主屏每一轮的任务、副屏每一轮的任务、执行、中断、连续
  交替、轮次列表。任务编辑防抖保存（`relay.dual_save`，不推进 revision）。
- **每轮是一次完整 Agent 对话**：后端 worker 调 `backend.send()`（与输入框发送
  同一条管道），工具、权限门、检查点、流式事件全部照常；事件带 `session_id`
  广播给本机连接，两屏各自渲染。工具需要确认时照常弹卡，接力停在等待状态。
- **交棒**：一轮结束后把「轮到谁」翻给对方，并把对方最近一次成功输出（最多
  6000 字符）写进下一轮的指令。勾选「连续交替」时 worker 自动跑下一轮，直到
  中断或出错；不勾选则每轮结束停在 idle，等用户点下一次执行。
- **中断**：取消 worker 与那一轮的 chat 任务（`cancel_run`），本轮记 cancelled、
  pair 停在 paused；再点执行从同一方继续（不重跑已完成轮次）。
- **状态与幂等**：idle / running / paused / interrupted；`relay_turns` 以
  (pair_id, turn_no) 为主键，开轮与推进都在独立短事务里做 revision CAS；
  `request_id` 幂等；数据目录独占锁沿用；重启把 running 的 pair 标 interrupted，
  不自动重放（重开会把同一条指令再发一次，可能重复执行工具）。
- **安全边界不变**：所有 `relay.dual_*` RPC `local_only`；主屏会话按项目归属
  校验（快聊按当前项目收编、跨项目拒绝）；两侧写入仍逐次经过 PermissionGate，
  接力不复制、不预授权任何权限。

接力的设置说明卡并入「设置 · 技能与工具」页（与圆桌 / 团队 / 对抗并列），只保留
使用说明与「打开接力工作台」入口；旧的 A/B 配置表单已移除（后端 `relaycfg.*`
仍保留给旧串行模式，无界面入口）。设置侧栏不再有独立的「接力」项。
