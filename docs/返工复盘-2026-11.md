# 返工复盘：Bug、返工、回滚与重复修改（2026-09-15 – 2026-11-18）

> 范围：`SkySheep` 主仓库 2026-09-15 至 2026-11-18 的 432 个提交，覆盖 2.6.x → 2.7.1
> 的完整发布周期。数据源：`git log`、`CHANGELOG.md`、`docs/release-notes/`、两份 README、
> 以及这两个月内的全项目评审、对抗审查、真实模型走查、历史包袱考古记录。
>
> 这不是一份「谁做错了什么」的清单。目的是找出**反复支付同一笔成本**的结构性原因，
> 并把能机械判定的部分变成测试、脚本和预检，而不是继续写在文档里靠人记。
>
> 口径说明：项目没有 issue tracker，缺陷数来自各轮评审/走查报告，严重度分级与统计口径
> 不完全一致，因此只做趋势与归因，不做精确同比；提交数按 `git log` 统计，含并行会话
> 合并进来的改动。

## 0. 结论先行

这两个月 432 个提交里有 **134 个 fix（31%）**。但真正贵的不是「写错再改」，
而是**改完还要重跑 10 分钟测试、重打 18–28 分钟发布链、甚至删 Release 重发**。
真正的 `Revert "..."` 提交是 **0 次**；只有 3 次带「撤销/回退」语义的处置
（版本号回退、撤销当日 Release、撤销一条产品限制）。绝大多数返工以
「fix forward + 补记 + 重发」的形式出现，所以从提交历史看像是「一直在修」，
而不是「回滚过一次」。

归因下来，返工集中在 8 类可预防问题，它们的共同点是：

> **项目里有大量「必须保持一致」的不变量，但只写在文档里、靠人记、靠人抄。**
> 主路径通常是对的，边缘路径成批漏；等真实模型/真实界面/真实发布链跑到时才发现。

这次把其中能机械判定的三类做成了守卫（版本号规则、消息字段契约、CHANGELOG 覆盖报告），
把跨边界的验收纪律和发布预检写进了 `AGENTS.md` 与发布 Skill；不能机械判定的，
写成了可对照的根因清单。

### 1.5 显式回退很少，返工以「重发」形式出现

| 提交 | 事件 |
|---|---|
| `953e249` | 版本号回退 2.6.5 → 2.6.4，本轮改动并入 2.6.4 打包 |
| `ac27939` | 撤销当日早发的 v2.6.0，删 Release 后重打替换（不走 `--clobber`） |
| `78558ce` | 撤销「至少保留一个项目」限制 |

**回退少不代表风险低**：版本号写错、Release 正文哈希不对、CHANGELOG 漏记，
这些都不适合 `git revert`，只能删 Release / 移 tag / 重打包 / 重上传。
一次这样的返工约等于一次完整发布（18–28 分钟构建 + 上传），而且会留下
「同版本号内容不同」的更新链路风险。

## 3. 八个共同根因

### R1. 并行事实来源：同一件事有几份手抄清单

**证据**
- `_msg_brief` 逐字段手写：`adversarial` 漏发（2026-10-21）、`system_note` 漏发（2026-11-12）、
  `sources`/`duration_ms`/`estimate` 漏发（2026-11-10）。
- 工具注解清单手写：`search_history` 漏了 MCP 四注解，点名清单也漏了它（全项目评审）。
- 静态文件清单三处：`index.html` script、`app.py` no_store、`sw.js SHELL_URLS`；
  六个拆分模块曾同时漏登记（审计 M18/L29）。
- 版本号七处：pyproject / `__init__` / installer.iss / uv.lock / CHANGELOG / 两份 README / index.html。
- 发布资产：安装包名、`.sha256`、Release 正文哈希、`engine/installer/` 只留现版+上一版。
- 内置技能数：`release.py` 的 `_GALLERY_SKILL_COUNT` 硬编码，技能包 20→22 时漏更（`2b621df`）。

**为什么反复**：新增字段/文件/方法时，人只记得改「主清单」，忘了旁边还有一份。
漏了不会报错，直到刷新页面、发版、或外部宿主读不到注解才暴露。

**防线**
- 优先从单一事实来源派生：Message 字段、`_WS_METHODS`、`index.html`、`Tool.__subclasses__()`。
- 必须保留并行清单时，加契约测试：`tests/test_message_brief_contract.py` 是本次新增的范例；
  `test_static_lists_stay_aligned_with_index_html`、`test_code_hygiene.py` 是既有范例。
- 发版前跑 `check_versions.py` 与 `check_changelog_coverage.py`。

### R2. 边界纪律靠自觉：主路径走 helper，边缘路径直接绕过

**证据**
- `textio` 是「非 UTF-8 文件不读坏/不写坏」的唯一入口，但 `subagent.py:1043` 仍直接 `write_text`；
  `config.init` 模板、`delete_pipeline`、`worktree exclude` 都曾绕过原子写/事务。
- `UnicodeDecodeError` 四处未捕（`subagent_store` / `subagent` / `team_resident`），
  启动直接崩；`load_mcp_configs` 到 2026-11-17 才补 GBK 兜底。
- `to_thread` 口径：`browser_data.py` 的 `rglob/rmtree` 曾阻塞事件循环，而 `data_retention.py` 已正确。
- `_write_txn` 口径：`store.delete_pipeline` 等多语句写曾不走事务。
- 权限门：并发只读批的 READOUT 分支缺 `_egress_scan`；prefix 白名单收窄只在一条路径用。

**为什么反复**：纪律写在 AGENTS.md 里，但每个新入口都要重新记得一次。
主路径有测试，边缘路径没有；评审时也只盯主路径。

**防线**
- 能机械判定的进 `test_code_hygiene.py`：`json.dump(` 禁止、工具注解必须显式、状态文件 GBK 容错。
- 新入口必须复用 `textio` / `_write_txn` / `to_thread` / `PermissionGate`；
  如果发现第二条实现路径，先收敛再写功能。
- 评审清单加一句：「这个改动有没有绕开已有 helper？边缘路径有没有同款处理？」

### R3. 测试只测组件，不测接缝

**证据**
- 协作三形态：单测覆盖了 `run_roundtable` / `run_adversarial` / `TeamOrchestrator`，
  但真实模型实测仍发现「模板吞 director_mode」「team:true 吞 grant」「队列只发给发起连接」
  「成员 Agent 的权限请求不进 `permission.queue`」。
- 接力：后端事件齐全，但副屏轮的事件与权限卡不进界面，导致卡到 300s 超时。
- 团队室未读 badge：单测过，真实多页签/后台起队场景下三处水位记账全错。
- 前端 wiring 测试大量用子串断言，`5dff9e4` 的旧断言被 setter 子串喂绿，抓不住真实调用点。

**为什么反复**：FakeProvider + 单连接 + 单 Agent 的测试，验证的是「组件自己能跑」，
不是「用户从界面上能看到、刷新后还在、换个连接也能收到」。跨边界功能的失败模式
恰恰在接缝上。

**防线**
- 跨界功能（圆桌/团队/对抗/接力/渠道/远程）的验收至少覆盖：
  1. 非发起连接也能收到事件；
  2. 刷新后权限卡可恢复；
  3. 成员 Agent 的请求也进队列；
  4. 失败/取消路径也有终态事件。
- wiring 测试锚真实调用表达式，不只断言函数名/字符串存在。
- 真实模型走查每轮至少跑一次「多连接 + 刷新 + 成员」组合，不只用单连接 FakeProvider。

### R4. 零构建前端 + 全局命名空间 + 手写序列化

**证据**
- `officialNote` 未定义 → 技能导入确认流程整体 `ReferenceError`（全项目评审高危）。
- `menu` 未声明 → 模板浮层选模板/确定当场抛错，链路在浏览器不可达（`5dff9e4`）。
- minimap 改名 `miniMsgs` → `miniMsgsFor` 时 `test_frontend_wiring` 红了一次。
- 接力面板解构层级错（后端扁平 pair 行）→ 刷新后面板不恢复。
- `_msg_brief` 漏字段 → 对抗卡/来源 chip/用时芯片刷新即丢。

**为什么反复**：没有类型系统、没有模块边界、没有编译期检查；改一个名字/搬一个文件，
只能靠 grep 和测试。而测试又常用子串断言，容易「看起来绿」。

**防线**
- 改名/搬移三步：grep 定义 + 全部调用点 + 测试锚点；不要只改定义。
- 新增 `app-*.js` 同步三处清单并递增 `SW_VERSION`（已有测试兜底）。
- 消息/事件新增字段先改序列化契约测试，再改前端。
- wiring/Playwright 测试优先用稳定 id/角色，不用用户文案——2.6.9 删掉一条成功 toast
  就让 `test_peer_pane_notices_stay_in_peer` 红在 CI，属于「文案当锚点」的典型代价。
- 关键交互用真实浏览器复验（agent-browser / Playwright），不只跑 `node --check`。

### R5. 环境状态耦合：数据目录、schema、分支、并行 WIP

**证据**
- 2026-11-06 一天内两次「库版本 N > 当前程序支持 M」启动锁死；2026-11-10 分支切回 main 再次触发。
- SEC-H01：测试未设 `SKYSHEEP_HOME`，直接读写真实 `~/.skysheep`。
- 并行会话活跃时 `git add -A` 把另一会话的 WIP 卷进提交（2026-09-21）。
- 并行 WIP 改了共享文件，导致全量测试出现「成员轮换」式假失败，需要先 `git status` 分清归属。

**为什么反复**：开发机上的 `~/.skysheep`、`~/.skysheep-dev`、临时 home、安装版数据目录
是四份状态；分支切换、打包版/源码版、并行会话都在改它们。没有默认隔离。

**防线**
- 开发验证一律 `SKYSHEEP_HOME` 指临时目录；测试由 `engine/conftest.py` 的 autouse fixture 隔离。
- 跨 schema 版本的分支不共用数据目录；切分支前换 `SKYSHEEP_HOME`。
- 并行会话活跃时先 `git status`/mtime 认领失败，禁止 `git add -A`。
- 启动日志保留「会话库已连接：路径（新建/已有，库版本）」，让锁死第一时间可诊断。

### R6. 发布流程是分布式状态机，但只有一部分被编码

**证据**
- 版本号七处、CHANGELOG、Release 正文、tag、资产名、`.sha256`、安装包目录、
  AGENTS.md 的版本引用，分散在脚本、文档、人的记忆里。
- 2.6.6 误发 2.7.0、2.6.10 误发、2.6.5 同日重发、3 次移 tag、4 次正文哈希更正、3 次 e2e 挂死。
- `release.py` 的 `_GALLERY_SKILL_COUNT` 硬编码，技能包增减时漏更。
- CI `pip-audit` 因漏洞库更新在无代码改动时转红 4 次（10-21、10-24、10-31、11-14）。

**为什么反复**：发布不是一次「点按钮」，而是一串跨天、跨工具、跨文件的状态转移。
脚本只覆盖了构建链，版本决策、CHANGELOG 完整性、正文口径、安装包清理仍靠人。

**防线**
- 版本号规则进 `check_versions.py`（本次新增「每段 0–9」）。
- CHANGELOG 覆盖进 `check_changelog_coverage.py`（本次新增）。
- 发布 Skill 把「预检 → 改号 → CHANGELOG → 正文 → 提交/tag → release.py → 发布后核对/清理」
  固化成步骤，并带失败手册（e2e 挂死、代理、LibreOffice python、tag 不一致、pip-audit）。
- 发布后必须提交 `release.py` 对正文 sha256 的自动修正；`engine/installer/` 只留现版+上一版。

### R7. 功能只加不减，历史包袱复利

**证据**
- 2026-11-17 历史包袱考古：53 项裁决，8 簇清理 42 文件 −922 行；
  仍有 relay v1、demo、set_manual、QUARANTINE、extension.audit.list 等 8 条决定保留。
- 死 CSS 23 类/18 组、死符号（`obs.span`、`describe_call`、`LMSTUDIO_BASE` 等）、
  v1.0 临时探针 5 个脚本，都是「当时先留着」留下的。
- 功能下线后文档/测试/CSS 不同步（场景模板下线、技能广场移除、工厂回放下线都做过收尾）。

**为什么反复**：加功能有明确收益，删功能有明确风险；「暂时保留」没有到期日。
半年后没人知道它是死代码还是休眠功能，只能再做一次考古。

**防线**
- 新功能上线时写清「替代/废弃关系」；下线功能同步删代码、测试、文档、CSS、SW 清单。
- 每季度做一次「零引用符号 + 死 CSS + 休眠功能」盘点；保留项写明理由与复查日期。
- 不把「本机单屏用不到」当作删功能面的理由（用户明确拒绝砍功能面）。

### R8. 验证太晚：评审/走查在实现之后，真实链路在发布之前

**证据**
- 全项目评审 96 条、UI 走查 24 条、协作实测 10+ 条，绝大多数是「实现完成后」才被发现。
- 真实模型走查发现的问题（接力确认、成员权限队列、团队室 badge）单测完全覆盖不到。
- 2.6.9/2.7.0 的 CI Playwright 红，是本机没装 Playwright、只能靠 CI 才发现（`a7ea6d1` 删 toast 后旧断言未改）。

**为什么反复**：项目把「实现 → 测试 → 评审 → 走查 → 发布」串行排列，
验证阶段天然滞后。静态评审能抓纪律，抓不到接缝；单测能抓组件，抓不到多连接。
两类验证都要，但都发生在成本已经付出去之后。

**防线**
- 把「接缝验收矩阵」前置到设计/实现时：跨边界功能先写 4 条接缝用例，再写主逻辑。
- 前端改动先在隔离实例用真实浏览器走一遍，再跑全量。
- CI 覆盖不到的（Playwright、真实模型、多连接）列入发布前人工验收项，不假设 CI 会兜住。

### 元根因：自声明纪律没有机械化

R1–R8 背后是同一句话：**规则写在 AGENTS.md 里，但执行靠人。**
主路径的人记得，边缘路径的人不记得；今天的人记得，下个月的人不记得。
所以这次的原则是：

> 能派生的不手抄；能断言的不用文档；能预检的不靠记忆；不能机械化的，写成可对照的清单。

## 4. 这次落地的防线

| 类型 | 落点 | 拦住什么 |
|---|---|---|
| 机械校验 | `engine/tools/check_versions.py` 新增「每段 0–9」 | 2.6.10 这类版本号，发布前直接红 |
| 契约测试 | `engine/tests/test_message_brief_contract.py` | `_msg_brief` 漏字段导致刷新后功能静默消失 |
| 发布预检 | `engine/tools/check_changelog_coverage.py` | 定版前漏记 feat/fix/perf；报告不拦，`--strict` 可拦 |
| 项目规则 | `AGENTS.md` 新增「返工防线」八条 | 把本次归因变成下次改代码前的对照表 |
| 发布 Skill | `.agents/skills/skysheep-release/SKILL.md` | 把发布步骤、正确解释器、失败手册固化 |
| 复盘文档 | 本文件 | 证据与取舍留档，避免下次重新考古 |

已有的守卫继续有效，不重复造：
`test_code_hygiene.py`（工具注解 / `json.dump` / GBK 状态文件）、
`test_frontend_wiring.py`（静态清单 / 加载顺序 / 接线）、
`test_local_only_methods.py` + `test_dispatch_gates.py`（WS 门禁）、
`conftest.py`（测试默认隔离 home）、`textio.py`（编码/原子写）。

### 没有做的，以及为什么

- **WS 方法清单 ratchet（342 个方法逐个分类）**：价值高，但一次性分类 342 个方法的
  远端语义需要产品/安全判断，容易做成「为了过测试而填表」。本次先保留 curated 清单 +
  新增方法人工评审；如果后续再出现「新方法静默远程可调」，再启动 ratchet。
- **前端未定义标识符静态分析**：零构建、无 ESLint，纯正则做 `ReferenceError` 检测误报太高
  （局部变量、解构、参数都会被误判）。继续用「真实浏览器走查 + wiring 测试锚真实调用点」兜。
- **SW_VERSION 内容指纹自动校验**：现有 `test_static_lists_stay_aligned_with_index_html`
  已保证新增文件必登记；「改了老文件忘升 SW_VERSION」仍靠流程，因为引入指纹基线会让
  每次前端改动都多一步机械更新，收益/摩擦比不划算。

## 5. 下次怎么用

### 改代码前（30 秒对照）

1. 这次改动会不会新增一份「需要和别处保持一致」的清单？→ 尽量派生；不能派生就加契约测试。
2. 有没有第二条路径绕开 `textio` / `_write_txn` / `to_thread` / `PermissionGate`？
3. 功能跨不跨主/副屏、团队/成员、渠道/远程？→ 先写接缝用例（多连接、刷新、成员）。
4. 改前端函数名/搬文件？→ grep 定义 + 调用点 + 测试；同步三处静态清单 + SW_VERSION。
5. 要动数据目录/schema？→ 换临时 `SKYSHEEP_HOME`，不切分支共用。

### 改完（项目纪律）

```bash
cd SkySheep/engine
uv run pytest -m "acceptance and not e2e" -q
uv run pytest -q tests/<受影响模块>.py
uv run ruff check .
# 改协议/前端再加
uv run pytest -m e2e -q
```

回复里写清命令、通过/失败/跳过数；不允许只写「测试通过」。

### 发版前

```bash
cd SkySheep/engine
uv run python tools/check_versions.py
uv run python tools/check_changelog_coverage.py --all
uv run python tools/check_release_notes.py ../docs/release-notes/<版本>.md --version <版本>
```

### 发版后

- 用 `gh api .../releases/tags/v<版本> --jq '.assets[]|{name,size,digest}'` 核对资产 digest；
- 提交 `release.py` 对正文 sha256 的自动修正；
- `engine/installer/` 只留现版 + 上一版；
- 同步 `Agent/AGENTS.md` 的版本引用与安装包描述；
- 看 main/tag 两条 CI。
