## 目标

把「贴一段报错」变成一次完整的排查：定位真凶、修好、验证，并留下排查报告——下次同类问题直接翻报告，不用从头再来。

## 使用时机

- 用户贴来一段报错信息、堆栈跟踪或截图，说「帮我看看」「这怎么回事」「修一下」。
- 用户描述程序行为异常（闪退、结果不对、卡住），愿意提供项目路径或相关文件。

## 执行步骤

1. **收集现场**：向用户确认三件事——报错的完整文本（堆栈一行都别截断）、发生在什么操作之后、项目路径。有路径就用 `list_dir` 看结构，用 `grep` 按报错里的关键类名/函数名搜代码。
2. **读懂报错**：从堆栈最后一帧开始读（那是抛出点），向上找第一帧属于用户自己代码的位置——那才是入口。区分三类：语法/环境错（缺依赖、路径不对）、逻辑错（空值、越界、类型）、外部错（网络、权限、文件占用）。
3. **定位根因**：读可疑代码的上下文（调用方、数据来源），别只看抛出那一行。能本地复现就复现：`run_command` 跑最小复现命令，确认报错可以稳定出现。
4. **最小修复**：改引起问题的那一处，不顺手重构、不扩大改动面。改完跑一遍复现命令验证报错消失，再跑一次正常路径确认没改坏别的。
5. **产出报告**：按下面的格式给用户一份排查报告，用户要留档时用 `write_document` 保存为 docx（先确认文件名和位置）。

## 输出格式

```markdown
# 排查报告：<一句话问题概括>

## 现象
<报错关键行 + 触发操作>

## 根因
<为什么会发生：直接原因 + 背后原因（如「空值未判」背后是「上游接口偶发返回 null」）>

## 修复
- <文件:位置>：<改了什么>，为什么这样改

## 验证
- 复现命令与结果（改前报错 / 改后通过）

## 防回归建议
- <如：补一个空值校验 / 加日志 / 上游接口加超时重试>
```

## 注意事项

- 不确定根因前不动手改代码；给出的是假设时，明确告诉用户「这是假设，验证方式是……」。
- 修复用最小改动：用户的项目不是重构现场，diff 越小越好审。
- 涉及依赖升级、全局配置改动的修复，先说明影响面再动手。
- 报错里可能带密钥、内网地址等敏感信息，写进报告前提醒用户脱敏。
- 修完建议用户提交一次检查点（会话里的检查点机制可回滚），方便不满意时回退。

## 常见问题

- 用户只给了一句「报错了」：列 3 个澄清问题（完整报错文本、触发操作、项目路径），不要凭空猜。
- 报错指向第三方库内部：先查是不是版本/用法问题（`web_search` 搜报错原文 + 库名），常见坑优先排除；确实库的 bug 就给绕行方案，不要去改库源码。
- 同样报错改了又出现：说明修的是表象，回到根因层重新定位；检查是否有多个调用路径、缓存或旧进程没重启。
- 用户环境跑不起来复现命令：退而求其次做静态定位（读代码 + 搜引擎），报告里注明「未能本地复现，结论基于静态分析」。
- 一段堆栈里出现多个报错：从最早的那个开始查，后面的往往是连锁反应。
