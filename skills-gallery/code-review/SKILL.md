## 目标

做一次「点得出具体位置」的代码审查：每条意见都落在文件和行号上，按严重度分级，让作者知道先修哪个、哪些可以以后再说。

## 使用时机

- 用户说「帮我审查一下代码」「看看这次改动有没有问题」「review 一下」。
- 用户给了代码文件、目录、diff，或贴了一段代码片段。

## 执行步骤

1. **圈定范围**：确认审什么——单个文件、整个目录还是一次改动（让用户说改动思路或给会话检查点 diff）。大目录先用 `list_dir` 看结构，挑核心模块先审。
2. **理解意图**：先读懂这段代码想做什么（注释、测试、调用方都是线索），带着「它想做什么」去看「它实际做了什么」，偏离意图的实现就是最典型的 bug。
3. **分四层过**：
   - **安全**：注入（命令/SQL/路径拼接）、密钥硬编码、越权访问、不安全的反序列化；
   - **正确性**：边界条件（空、零、极大）、错误处理吞异常、并发与资源泄漏、时区与编码；
   - **可维护性**：命名说谎、重复逻辑、过长函数、魔法数字；
   - **一致性**：与项目既有风格是否冲突（先看旁边代码怎么写，别拿通用标准硬套）。
4. **逐条定位**：每个问题用 `文件:行号` 定位，给出「问题 → 影响 → 建议」；建议给方向也尽量给改法示例。
5. **输出报告**：按严重度分级输出；用户需要时用 `write_document` 存档或直接逐条修复（修复走写文件确认流程）。

## 输出格式

```markdown
# 代码审查：<范围>（共 N 处：高 X / 中 Y / 低 Z）

## 高（可能造成事故，建议立即处理）
- **`path/file.py:42`** <问题一句话>
  影响：<会发生什么>
  建议：<怎么改，附示例代码>

## 中（隐患，本次或下次迭代处理）
- …

## 低（锦上添花）
- …

## 亮点
- <值得保持的好做法，审查不只挑刺>
```

## 注意事项

- 每条意见必须落到具体行号，不写「整体感觉不够优雅」这类没法执行的话。
- 不确定的问题标注「待确认」并给出验证方法，不把猜测写成断言。
- 尊重项目现状：风格问题服从项目既有约定；没有约定的小问题降级为低。
- 审查 ≠ 重写：除非用户明确要求，不整段重写别人的代码，改动建议以小步为准。
- 发现疑似密钥/凭据，提醒用户立即轮换，而不仅仅是「从代码里删掉」。

## 常见问题

- 用户只贴片段没有上下文：审片段本身的问题，涉及调用方行为的标「需结合上下文确认」。
- 代码能跑但写得乱：区分「错」和「丑」——能跑的先审正确性与安全，风格建议集中放低档，别把审查变成品味批评。
- 意见太多不知从哪改起：给一个建议顺序（先高危、再测试盲区、后风格），并主动提出「要不要我按这个顺序逐条修」。
- 用户对某条意见不认同：摆出依据和反例，认同对方的场景解释，把分歧记为「讨论后保留现状」。
- 测试缺失明显：单列「测试盲区」小节，给出最值得补的 3 个用例，不要求全覆盖。
