## 目标

帮用户在几分钟内产出一封可以直接发给上级或团队的中文周报，做到：内容具体、有数据支撑、结构清晰、不夸大不遗漏。

## 使用时机

- 用户说「写周报」「整理一下这周干了什么」「生成 weekly report」。
- 用户给出若干零散记录（笔记、聊天记录、任务清单、commit 列表等），要求汇总成周报。

## 执行步骤

1. **收集素材**：先问用户本周做过哪些事。如果用户给了记录文件路径（Markdown、txt、csv 等），用 `read_file` 读取；如果用户指定某个项目目录，用 `list_dir` 和 `glob` 查看文件结构，用 `grep` 搜索本周改动的关键词；如果用户直接口述，边听边记要点。
2. **澄清口径**：确认三件事——周报时间段（本周一至周五还是自然周）、汇报对象（直属上级 / 全组 / 跨部门）、是否需要控制篇幅（一页以内还是详细版）。
3. **归纳提炼**：把素材按主题归并（如「项目 A」「日常维护」「协作支持」），每件事尽量带上量化结果（完成度、数量、耗时变化、对比上周期）。没有数据支撑的表述宁可不写数字，也不要编造。
4. **撰写周报**：按下面的输出格式组织内容，先在对话里以 Markdown 呈现，请用户确认或修改。
5. **保存文档（可选）**：用户需要文件时，先确认文件名和保存位置，然后用 `write_document` 生成 .docx（正文用 Markdown 子集：#/## 标题、段落、- 列表、| 表格 |、**加粗**）。写文件会弹出确认框，属正常流程。

## 输出格式

```markdown
# 周报（YYYY-MM-DD ~ YYYY-MM-DD | 姓名）

## 本周成果
- **<主题 1>**：<做了什么>，<结果/进展，尽量量化>
- ...

## 数据与进展
| 事项 | 关键数据 | 较上期 |
| --- | --- | --- |
| ... | ... | ... |

## 下周计划
- <计划事项>（预计完成时间 / 优先级）

## 风险与求助
- <风险或阻塞>：影响、应对建议、需要谁的支持
```

- 没有风险的周可以写「本周无阻塞事项，进展顺利」，但不要留空标题。
- 「数据与进展」没有表格数据时可并入「本周成果」，用要点呈现。

## 注意事项

- 只基于用户提供的信息和文件内容撰写，不虚构数据；数字拿不准时向用户复核。
- 语气客观克制，避免「圆满完成」「极大地」等夸饰词；成果用事实说话。
- 涉及他人或敏感信息（人事、薪酬、未公开项目）时，先提醒用户确认是否适合写入周报。
- 生成 docx 前必须与用户确认文件名与保存位置。
- 如果用户开启了记忆，可以在征得同意后用 `memory_write` 记住周报的固定格式和汇报对象偏好，下次直接套用。

## 常见问题

- 用户说「就随便写写」：仍按四段结构走，但篇幅压缩到各段 2–3 条，先出短版再按反馈扩写。
- 素材里找不到量化数据：列出「待补数据」清单请用户填写，占位写成 <待补：本周新增用户数>，不要自己估数。
- 用户要同时交周报和月报：先确认两个周期的边界，避免同一件事重复计入两份报告。
- 上周计划要跟踪兑现：请用户提供上周周报（`read_file` 读取），新增「上周计划完成情况」小节逐条对账。
- 用户所属团队有固定模板：模板文件用 `read_file` 读取后严格套用其章节顺序，不要自创结构。
- 需要英文版周报：先交付中文定稿，确认后再整体翻译，不要中英混排。
- 用户只要口头发周会：压缩成 5 句以内的口头版（做了什么 / 关键数字 / 下周重点 / 需要的支持）。
- 收集阶段用户迟迟没给素材：列出 3–5 个引导性追问（本周推进了哪个项目、卡在哪、帮了谁），帮用户回忆。
